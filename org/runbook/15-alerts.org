#+TITLE: Every alert, what it means, and what to do
#+SUMMARY: The full alert catalogue with the first command and the fix for each — plus the ones that are a trap if you react before reading.
#+GROUP: Recovery

Alerts come from two places, and they behave differently:

- *Prometheus rules* (56) are evaluated centrally. They have a =for:= duration, so
  they mean "this has been true for a while", and they clear themselves when the
  condition clears.
- *Pushed alerts* (8) are sent by systemd hooks on the host: a failed backup, a
  failed smoke test, a stale generation. They carry no =endsAt=, so Alertmanager
  resolves them ~5 minutes after the last push. *"Resolved" for a pushed alert
  means "not re-pushed", not "fixed".* The summary says so.

To see what is firing right now:

#+begin_src sh
curl -s http://127.0.0.1:30903/api/v2/alerts | jq -r '.[] | "\(.labels.alertname) \(.labels.instance // .labels.unit // "")"'
#+end_src

* Triage order when several fire at once

1. *EtcdQuorumAtRisk* — everything else is noise if the control plane is going.
2. *NodeDown* — is a machine actually gone, or just its exporter?
3. *CloudflareTunnelDown / PublicProbeDown* — is the edge out?
4. *WireGuardNoEgress* — is the media node cut off?
5. *MediaBranchCritical* — imports are about to fail.
6. *LonghornDiskSchedulingOverCommitted* — the next replica rebuild on that disk fails.
7. The rest are degradations: read, schedule, do not page yourself at 3am.

* Infra

| Alert | Sev | Means | Fix |
|-------+-----+-------+-----|
| =NodeDown= | crit | node-exporter stopped reporting for 5m | =ping=/=ssh= the host first. Up but no metrics → =kubectl -n monitoring rollout restart ds/node-exporter=. Down → power, then check quorum (page 12) |
| =TargetDown= | warn | some scrape target is unreachable (kubelet-cadvisor and longhorn excluded — they have their own) | =curl -s .../api/v1/targets \| jq '.data.activeTargets[] \| select(.health!="up")'= |
| =DiskFillingUp= | warn | a non-media filesystem is >85% | =nix-collect-garbage -d=, =journalctl --vacuum-time=14d=, check Longhorn replicas |
| =HostMemoryHigh= | warn | >90% available used for 15m | =kubectl top pods -A --sort-by=memory \| head= |
| =RootFilesystemDaysToFull= | warn | =predict_linear= says the root filesystem fills within 7 days | page 21 step 1: image prune + =nix-collect-garbage=. The root filesystem carries etcd |
| =MediaBranchFillingUp= | warn | *one mergerfs branch* is >85% — the pool union hides this | rebalance, page 09 step "a branch is full" |
| =MediaBranchCritical= | crit | branch >93%; mergerfs refuses creates under 4G free | free space *now*; imports will fail mid-write otherwise |
| =MediaPoolFillingUp= / =MediaPoolCritical= | warn/crit | the union is >85% / >92% | reclaim with the *arr cleanup, or add a disk |
| =MediaPoolDaysToFull= | warn | =predict_linear= says 7 days | same as above, but you have a week |
| =StrayCNIAddress= | warn | an interface that is not Cilium held an address inside the pod CIDR; the sweep removed it | read the journal tag =cni-stray-sweep=; any pod on that address was unreachable. See =NETWORK.md= invariant 9 |
| =StrayCNIMetricsMissing= | warn | the sweep stopped reporting for 90m | =systemctl list-timers cni-stray-sweep=; check =/var/lib/node-exporter/textfile/stray-cni.prom= is world-readable |

* etcd

| Alert | Sev | Means | Fix |
|-------+-----+-------+-----|
| =EtcdNoLeader= | crit | this member has no leader 2m in | if one member: it will rejoin; if all: quorum loss, page 12 |
| =EtcdMemberUnreachable= | warn | <3 members reporting | =kubectl -n kube-system get pods -l component=etcd=; usually the third node is rebooting |
| =EtcdQuorumAtRisk= | crit | <2 leaders — writes are failing or about to | *stop everything else*, restore a member, never take a second one down |
| =EtcdHighFsyncLatency= | warn | WAL fsync p99 >500ms, the disk is the bottleneck | check =iostat -x 1= on that node; Longhorn + etcd on one disk is the usual cause |

* Storage (Longhorn)

| Alert | Sev | Means | Fix |
|-------+-----+-------+-----|
| =LonghornVolumeDegraded= | warn | one replica is gone or rebuilding | tolerated, but do *not* lose the second one: find out why before touching anything |
| =LonghornVolumeFaulted= | crit | the workload has no data | page 21, and check the node did not just die |
| =LonghornVolumeUnknown= | warn | Longhorn cannot decide the volume's health | check the volume in the Longhorn UI; usually one node unreachable |
| =LonghornDiskSchedulingHeadroomLow= | warn | >90% of a disk's *remaining free space* is already promised to replicas, held for an hour | page 21 steps 2 and 3 |
| =LonghornDiskSchedulingOverCommitted= | crit | >100% — more promised to replicas than exists free | page 21 step 2 *now*; the next rebuild on that disk fails |
| =LonghornDiskStorageLow= | warn | actual usage >90% of capacity | page 21 step 1, then step 3 |
| =LonghornNodeStorageLow= | warn | whole-node Longhorn usage >85% | as above; the per-disk rules are the real signal |
| =LonghornScrapeFailing= | warn | no metrics from that node's manager | every Longhorn rule above is blind while this is red |

There is deliberately no alert for "Longhorn holds replicas on the OS filesystem":
every node here does, so it would be permanently red. It is a *panel* (Longhorn on OS
filesystems) and a migration decision in =NEXT-STEPS.md=, not a page.

=LonghornDiskStorageLow= compares usage to capacity, which is *not* what stops a
rebuild. On 2026-10-30 a disk holding 45 G of replicas had 120 MiB left for the
next one and read 43% "used". The two headroom rules and the recording rule
behind them exist because of that — page 21 explains the number.

* The three that are a trap

*Do not restart =wg-quick-proton0=.* It is the cause of seven outages, not the
fix. =WireGuardNoHandshake= and =WireGuardNoEgress= both have safe procedures
(pages 11 and 14) that never touch the unit.

*Do not delete a crash-looping pod first.* =KubePodCrashLooping= with restart
count 6 and exit code 0 means something is *killing* a healthy process — probes,
OOM, or an address that belongs to the node. Deleting the pod hides the evidence
and, if the cause is deterministic, recreates it.

*Do not treat a pushed alert's "Resolved" as recovery.* It expires ~5 minutes
after the last failure report. If =BackupFailed= resolves but no backup ran, the
backup still did not run.
