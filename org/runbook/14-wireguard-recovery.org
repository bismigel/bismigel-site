#+TITLE: WireGuard recovery and reboot-proofing
#+SUMMARY: Recover the media node's tunnel after a reboot or a stranded activation, and the rules that keep it from stranding again.
#+GROUP: Recovery

* Read this with =NETWORK.md= open

=NETWORK.md= in the homelab repo is the authoritative network reference. This
page is the procedure; that page is the truth about the network.

* The shape of the problem

=calamansi-intel= (192.168.2.81) has **no direct internet**. Every packet leaves
through a WireGuard full tunnel to Proton (=proton0=). Three consequences:

1. If the tunnel is not passing data, the node has no egress at all.
2. *A handshake is not a working tunnel.* With the wrong private key WireGuard
   still handshakes and blackholes the payload.
3. Restarting the tunnel is safe *only because* its policy rules carry explicit
   priorities since 2026-10-28. The old =wg-quick= unit did not, and restarting
   it stranded the node seven times in one night — see *The rule that keeps it
   up* below before you change anything about =wireguard-proton0=.

* Symptom → what to do

| Symptom | Cause | Action |
|---|---|---|
| Node unreachable, ARP answers, nothing above L2 | tunnel rules landed above =local= (the pre-2026-10-28 =wg-quick= bug) | physical power-cycle, then *After a reboot* |
| SSH works, egress =000= | tunnel up, no data path | §"Restore without restarting" |
| SSH works, egress fine, ~15 s dead at boot | reconciler swapping seed → declared peer | wait, it is expected |
| =wg show= has a fresh handshake but egress =000= | stale private key | compare fingerprints (§"Verify") |

* Verify before you touch anything

#+begin_src sh
# is there really no egress? (control targets, not one site)
for h in registry.npmjs.org example.com; do
  printf '%-22s ' "$h"; curl -sS -o /dev/null --connect-timeout 8 -w '%{http_code}\n' "https://$h/"
done

# does the interface key match the key in SOPS?
tr -d '\n' < /run/secrets/wg_proton_private_key | sha256sum | cut -c1-16
wg show proton0 private-key | tr -d '\n' | sha256sum | cut -c1-16   # must match

# is the endpoint reachable OUTSIDE the tunnel?
ip route get 176.113.74.82

# data path, not just a handshake
wg show proton0 | grep -E 'endpoint|latest handshake|transfer'
#+end_src

* Restore without restarting

The staged recovery script swaps key and peer **in place** (=wg set=), never
tearing the interface down. It is at =/root/wg-restore.sh= with the key at
=/root/wg.key=:

#+begin_src sh
ssh root@192.168.2.81 \
  'KEYFILE=/root/wg.key EXPECT_FP=1795227bcb589e43 /root/wg-restore.sh'
#+end_src

It verifies the key fingerprint first, removes peers that are not pointed at
=176.113.74.82=, sets the declared peer, waits for a handshake, and probes the
data path. Expect =egress: 200= within ~30 seconds.

If =/root/wg.key= is gone, run it with the SOPS secret instead (default path):

#+begin_src sh
ssh root@192.168.2.81 '/root/wg-restore.sh'
#+end_src

* After a reboot — it should heal itself

Since 2026-10-28 a reboot is part of the acceptance test, not a risk: the tunnel
is a normal =networking.wireguard= unit whose policy rules carry explicit
priorities, so nothing about bringing it up can strand the node.

Verified on 2026-10-28 (twice): tunnel active and egress =301= within ~40 s of
boot, node =Ready= within ~20 s of k3s starting.

*Two failures only ever appear at boot*

Both were found by rebooting, not by deploying. If a reboot misbehaves, check
these first:

1. =wireguard-proton0= failed with =Error: Nexthop has invalid gateway=. The
   endpoint route was added before NetworkManager had configured =eno1=; the unit
   is =Type=oneshot= so that failure is final and the node boots with **no
   egress**. =postSetup= now retries the pin for 60 s, and =nix flake check=
   asserts the retry is still there. If you ever see it, start the unit by hand
   once the link is up: =systemctl start wireguard-proton0=.
2. The node comes back =NotReady= and =k3s= logs
   =ClientURLs:[https://10.2.0.2:2379]=. k3s auto-detected its address from the
   default route — which is the tunnel — so etcd advertised an address no peer can
   reach and the member never rejoined. Fixed by pinning =--node-ip= and
   =--advertise-address= to =192.168.2.81= (NETWORK.md §7.4).

The reconciler runs at =90 s= after boot and every =60 s= after that. It pins the
endpoint route, makes the interface key match SOPS, removes stale peers, sets the
declared peer, and probes the data path.

If egress is still dead three minutes after a boot:

#+begin_src sh
systemctl status wireguard-proton0 --no-pager
ip rule show | head -5
systemctl list-timers --all | grep wireguard-reconcile
journalctl -u wireguard-reconcile.service -n 20 --no-pager
#+end_src

A verdict of =ok (handshake Ns, data path HTTP 301)= is healthy (=301= is
correct: =https://1.1.1.1/= redirects).

* The rule that keeps it up

The tunnel is =networking.wireguard= since 2026-10-28: one declaration in
=modules/wireguard-native.nix=, no =wg-quick= block, no boot seed.

What must not be lost is the *reason* the old =wg-quick= unit could not be
touched. =wg-quick= adds its policy rules with =ip rule add= and no explicit
priority, and the kernel derives that priority from the rule list
(=fib_default_rule_pref()= returns the priority of the *second* rule, minus one).
Cilium leaves a rule at priority 9 and =local= at 100, so the tunnel's rules
landed at **98/99 — above =local=**. Packets to the node's own LAN address were
then routed out of the interface instead of being delivered locally: the node
stopped answering its own IP, ARP kept working, and only a power-cycle recovered
it. Seven times on 2026-10-25.

The fix is two words: =pref 32765= and =pref 32764=. =postSetup= in the native
module carries them, =scripts/wg-fallback.sh= carries them, and
=nix flake check= asserts they are still there. Removing them restores the bug.

Restarting the tunnel is now routine — verified 3× on production on 2026-10-28
with rules at 32764/32765, gateway reachable, egress 301 and a fresh handshake
each time:

#+begin_src sh
systemctl restart wireguard-proton0
ip rule show | head -5
#+end_src

The live state still belongs to =bakuran.wireguard=
(=modules/wireguard-reconcile.nix=): endpoint =176.113.74.82=, peer =nLx6…=,
=allowedIPs 0.0.0.0/0=. It enforces that in place with =wg set=, every 60 s.

* Rolling back

**Do not roll back with =wg-quick up=.** It re-adds the rules without =pref=,
which is the outage. Use:

#+begin_src sh
CONF=/root/proton0-fallback.conf scripts/wg-fallback.sh
#+end_src

That rebuilds the interface with =ip link add= + =wg setconf= from a
=wg showconf= snapshot and installs both rules with their priorities pinned.
The snapshot =/root/proton0-fallback.conf= was saved on 2026-10-28 while the
tunnel was healthy; save a fresh one (=wg showconf proton0=) after any endpoint
or key rotation.

* History: how the cutover was done (2026-10-28)

Kept because the shape recurs: rehearse, then replace the unit with a human at
the box.

1. Rehearse in =staging-vm= with Cilium installed, booting the *real* module —
   the shell imitation proves the mechanism, not the artifact
   (=staging/cluster-3node/native-test.nix=).
2. Stage the fallback: =wg showconf proton0 > /root/proton0-fallback.conf=.
3. Delete the =networking.wg-quick.interfaces.proton0= block *and* the
   =systemd.services."wg-quick-proton0"= override; set
   =bakuran.wireguard.useNative = true=.
4. =scripts/preflight-wg.sh= now names this case (it used to say "cannot tell")
   and still refuses it — the refusal is correct, override it knowingly.
5. Deploy with someone able to power-cycle the node.
6. Verify: rules at 32764/32765 *with Cilium's rule 9 present*, =ip route get
   192.168.2.81= via =local=, =wg show proton0 latest-handshakes= fresh,
   egress =301=, Cilium 3/3, then restart the unit three times.

* Do not

- Do not =systemctl restart wg-quick-proton0= on a node you cannot reach.
- Do not rotate the endpoint to "fix" egress; the endpoint was never the problem.
- Do not re-add =::/0= to =allowedIPs= (the boot seed in the host file keeps it
  only so its unit stays byte-identical; the reconciler enforces IPv4-only).
- Do not report "no data path" from a check that demands exactly HTTP 200.
- Do not trust a handshake as proof of a working tunnel.
