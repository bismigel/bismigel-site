#+TITLE: A secret has drifted from Bitwarden
#+SUMMARY: How to find the Secrets nothing reconciles, and how to hand one to ESO without a moment of downtime.
#+GROUP: Platform

A Secret written by hand has no state anyone can check. It does not fail; it
*stays*. On 2026-10-29 two of them were found in the same namespace, and the only
reason the credentials still worked was that nobody had re-run the script that
created them since the volume they belonged to was restored from backup.

* How to find one

#+begin_src sh
# every Secret ESO manages carries this annotation
kubectl get secrets -A -o json \
  | jq -r '.items[] | select(.metadata.annotations["external-secrets.io/managed"] != "true")
           | "\(.metadata.namespace)/\(.metadata.name)"'
#+end_src

A Secret in that list is either intentionally seeded (there are two: `media-setup`,
`usenet-frugal`) or a liability. Check it before assuming the second.

* Handing one to ESO (adopt, do not replace)

The rule is one sentence: **the value must not change**, and no consumer may see the
object disappear. `creationPolicy: Owner` gives you both — ESO updates the existing
Secret in place and adds its owner reference.

1. **Hash what is there now.** Do not print it.
   #+begin_src sh
   kubectl -n <ns> get secret <name> -o jsonpath='{.data.<key>}' | base64 -d | sha256sum
   #+end_src
2. **Write the ExternalSecret**, with the same `target.name` and the same keys.
   Maps to Bitwarden through the cluster's `ClusterSecretStore` — which works in
   *every* namespace, so "there is no ESO here" is not a reason.
3. **Merge and let it sync.** Then confirm all three things:
   #+begin_src sh
   kubectl -n <ns> get externalsecret <name>            # SecretSynced/True
   kubectl -n <ns> get secret <name> -o jsonpath='{.metadata.ownerReferences[*].name}'
   kubectl -n <ns> get secret <name> -o jsonpath='{.data.<key>}' | base64 -d | sha256sum
   #+end_src
   The owner reference is the ExternalSecret, and the hash is **identical**. If the
   hash changed, the store and the cluster had already diverged — find out why before
   anything restarts, because the old value was working.
4. **Delete the thing that used to write it** (the seed script, the shell alias, the
   README paragraph that tells people to run it). Otherwise it comes back.
5. **Record the credential in the consumer's runbook** — the nightly job, the init
   container — so the next reader knows where it comes from.

* Do not do this to `media-setup` casually

`media-setup` is read during first boot by workloads that may come up before ESO is
ready. Adopting it is possible, but the ordering has to be reasoned about; the
current answer is that it stays a seeded Secret and that fact is written down.

* Gotchas

- **A missing remote key is not a no-op.** ESO reports `SecretSyncedError`, ArgoCD
  counts that Application as unhealthy, and if it is in a smoke test you get paged
  all night. Add the Bitwarden key first, the manifest second — or hold the manifest
  behind a comment until the key exists.
- **Adopting is not rotating.** `creationPolicy: Owner` keeps the current value.
  Rotation is a separate act: change the source, then restart the consumer.
- **`optional: true` hides the failure.** Useful for an optional second password;
  wrong for a credential the workload needs to start.
