#+TITLE: Change the router without clicking
#+SUMMARY: Two loops for OPNsense: OpenTofu for objects, the Ansible baseline for settings with no provider resource — credentials, adoption by import, the traps that make a green apply a lie, and how to roll back.
#+GROUP: Operations

On 2026-11-01 the DHCP DNS servers had to change: the nodes were resolving through
=1.1.1.1=, which on the media host is routed *inside* the WireGuard tunnel, so an
egress fault became a DNS fault and forty pods landed in =ImagePullBackOff=.

The first two attempts were hand-written API calls to the live DHCP server. Both
returned =Unexpected error=, and guessing write payloads against the thing that
hands out every address on the LAN is not a trade worth making. The declarative
path existed all along — it needed a state backend, not a new tool.

* What you need before you start

  | Thing | Where |
  |-------+-------|
  | OPNsense API key | Bitwarden Secrets Manager, project =homelab-kube=: =opnsense-api-key= and =opnsense-api-secret=. Read them by *secret id* — the ids are in =bakuran-infra/opentofu/opnsense/README.md= |
  | R2 credentials for the S3 state backend | the *same* key the backup job uses, in =/root/.config/homelab-backup.env= on the platform host |
  | OpenTofu | =nix run nixpkgs#opentofu -- …= |

  No new credential is needed for state: the backend bucket (=homelab-backups=) and
  endpoint are the ones the nightly backups already write to. Map the R2 names onto
  the AWS ones, nothing else:

  #+begin_src sh
  ssh root@<platform> 'grep -E "^R2_(ACCESS_KEY_ID|SECRET_ACCESS_KEY)" /root/.config/homelab-backup.env' \
    > ~/.config/opentofu/r2.env
  chmod 600 ~/.config/opentofu/r2.env
  #+end_src

  #+begin_src sh
  set -a; . ~/.config/opentofu/r2.env; set +a
  export AWS_ACCESS_KEY_ID="$R2_ACCESS_KEY_ID"
  export AWS_SECRET_ACCESS_KEY="$R2_SECRET_ACCESS_KEY"
  export AWS_DEFAULT_REGION=auto
  # pre-2026-11-03 this read a file that held 'key=<80 chars>' / 'secret=<80 chars>'
  # lines and stripped the prefix with grep -oP '(?<=key=)'. The file is gone; the pair
  # now comes from the vault (see "The API itself"), which avoids that parsing entirely.
  . ~/projects/bakuran-infra/opentofu/opnsense/env.sh
  export TF_VAR_opnsense_uri="https://192.168.2.1"
  #+end_src

  Symptom if you skip this: =tofu init= fails with
  =no EC2 IMDS role found, operation error ec2imds: GetMetadata= — that is the S3
  backend looking for credentials, not a provider problem.

* The loop

  1. **Write the change in =opentofu/opnsense/=.** If the object already exists in
     the router, use an =import= block — never let tofu create a second one.
  2. **=tofu init=** once per working copy.
  3. **=tofu plan= and read it.** This is the only step that catches a wrong
     declaration before it reaches the router.
  4. **=tofu apply=**.
  5. **=tofu plan= again.** It must say *No changes*. If it does not, the state and
     the router disagree and the change is not finished.
  6. **Commit.** The plan output belongs in the PR description, because it is the
     evidence that the apply did what the diff said.

* Adoption: read the first plan, do not assume

  The subnet had been deliberately unmanaged ("pools we do not want to bake in").
  Adopting it is an =import= block plus a resource whose attributes match what is
  already there:

  #+begin_src hcl
  import {
    to = opnsense_kea_dhcpv4_subnet.lan
    id = "4a1b6c22-1111-4aaa-8bbb-000000000001"
  }
  #+end_src

  The **first plan is a census of what you did not know.** It reported two things
  worth reading rather than discovering later:

  - the live description was ="homelab LAN"= — declaring =""= would have silently
    cleared a field nobody meant to touch;
  - the pool was stored as =192.168.2.150-192.168.2.240= and the provider wants the
    spaced form =192.168.2.150 - 192.168.2.240=.

  After the import applies, the plan must show **only** the change you intended.

* Two traps that make a green apply a lie

  **1. =dns_servers= is a =Set=, so order is lost.** Asking for
  =["192.168.2.1", "1.1.1.1"]= applies as =1.1.1.1,192.168.2.1= — alphabetically
  sorted — and Kea sends them in that order. Clients then try the tunnelled resolver
  *first*, which defeats the entire change while every command reports success.
  There is no ordered alternative resource in the provider, so hand out **one**
  resolver and move the fallback into unbound's upstreams.

  **2. =auto_collect= must be =false=.** With it on (the default), OPNsense keeps the
  subnet's option data in sync from the interface configuration and
  **=routers=, =dns_servers= and =ntp_servers= are ignored** — the apply reports
  success and changes nothing. Verified by applying both ways, same day.

  Both are the same shape as the other traps in this estate: *a change that cannot
  fail is a change that never happened.* Read the router back after an apply, every
  time.

* Verify — read the router, not the exit code

  #+begin_src sh
  # DNS servers Kea is actually offering the LAN
  curl -sk -u "$KEY:$SECRET" https://192.168.2.1/api/kea/dhcpv4/searchSubnet \
    | jq -r '.rows[0].option_data.domain_name_servers'
  # the two things that must not have moved
  curl -sk -u "$KEY:$SECRET" https://192.168.2.1/api/kea/dhcpv4/searchSubnet \
    | jq -r '.rows[0] | .pools, .option_data.routers'
  # the service is still serving
  curl -sk -u "$KEY:$SECRET" https://192.168.2.1/api/kea/service/status | jq -r .status
  #+end_src

  Then from a DHCP client after its next renewal:
  =resolvectl status | grep 'DNS Servers'=. A DHCP client only picks the new value
  up when its lease renews — a static host never will, and =.81= needed an hour.

* Rollback

  Revert the commit, =tofu apply=, and the router returns to the previous values —
  that is the whole point of state. If the router itself is wedged, the config export
  taken before the change restores it whole:

  #+begin_src sh
  curl -sk -u "$KEY:$SECRET" https://192.168.2.1/api/core/backup/download/this \
    > ~/router-stage/config-backup-$(date +%Y-%m-%dT%H%M).xml
  chmod 600 ~/router-stage/config-backup-*.xml
  #+end_src

  **Take that export before any DHCP change**, without exception. It contains the
  WebGUI TLS key and the root password hash, so it belongs in =~/router-stage/= and
  never in a repository — the repo's =.gitignore= refuses =*.xml= for exactly this.

* The API itself

  Everything the UI does is an HTTP call, and it is the only scriptable path.

  | | |
  |---+---|
  | base | =https://192.168.2.1/api/<module>/<controller>/<action>= |
  | auth | HTTP Basic, =key:secret= — from =System -> Access -> Users -> root -> API keys= |
  | TLS | self-signed, so =curl -k= |
  | liveness check | =GET /api/core/firmware/status= expecting =200= |

  #+begin_src sh
  . ~/projects/bakuran-infra/opentofu/opnsense/env.sh   # loads the pair from the vault
  curl -sk -u "$TF_VAR_opnsense_api_key:$TF_VAR_opnsense_api_secret" \
    https://192.168.2.1/api/core/firmware/status
  #+end_src

  *Five traps, all hit on 2026-11-03:*

  - *The exported key file has =key== / =secret== prefixes.* Taking the whole line gives
    an 84-character "key" and a 401 that looks like a revoked credential. The stored keys
    are 80 characters. Strip the prefix — or better, read the pair from the vault and stop
    parsing files.
  - *The UI login is TOTP-protected.* =root= has =otp_seed= set, so there is no headless
    username/password route, and a session POST additionally needs =X-CSRFToken=. API keys
    are the only automation path; do not go looking for a login flow.
  - *A key is shown once.* Close the dialog without copying the secret and the key is
    unusable forever — OPNsense keeps only a hash.
  - *Nothing on the CLI mints a key.* With zero keys, use the UI, or call the same model
    from a root shell:
    #+begin_src php
    $model = new \OPNsense\Auth\User();
    $model->getUserByName('root')->apikeys->add();   // returns key + secret
    $model->serializeToConfig(false, true);
    \OPNsense\Core\Config::getInstance()->save();
    #+end_src
  - *There are two firewall config paths.* =$config['filter']['rule']= holds the legacy LAN
    defaults; the CLIENTS rules live in
    =$config['OPNsense']['Firewall']['Filter']['rules']['rule']=. Reading the first reports
    "0 rules" and looks exactly like a missing policy.

  Deleting a key: =POST /api/auth/user/delApiKey/{base64(key)}= — the id is the key itself,
  base64-encoded. *Check that a key is genuinely dead before deleting it:* count the keys
  on the box first, and re-test with the prefix stripped.

* The baseline: what the provider cannot reach

  OpenTofu covers VLAN 20, the Kea subnet/pool/DNS, the DHCP reservations and the four
  CLIENTS firewall rules. Everything else on the router is either in the Ansible baseline
  or genuinely manual - and =tofu plan= saying "no changes" says nothing about it.

  #+begin_src sh
  cd bakuran-infra/network/ansible
  ansible-playbook -i inventory.yml playbooks/opnsense.yml -e audit=1   # change nothing
  ansible-playbook -i inventory.yml playbooks/opnsense.yml              # correct drift
  #+end_src

  Read the =msg= array: each line is a separate assertion.

  | assertion | why it exists |
  |-----------+---------------|
  | SSH keys, password auth off, WebGUI timeouts | access policy with no provider resource |
  | Kea serving interfaces | the interface list is a plugin setting, not a Kea subnet |
  | =/etc/cron.d/dnsbl= and =/etc/cron.d/homelab-heartbeat= | *not* in a config backup - =/conf/config.xml= is, =/etc= is not - and they cannot be OPNsense cron jobs either, because that plugin only accepts registered configd actions |
  | gateway monitor IP =1.1.1.1= | the ISP gateway drops ICMP, so monitoring it reports a permanent outage |
  | Unbound =dnssec= | off means silently unvalidated |
  | DNSBL entry =oisd0= (=nxdomain=, =cache_ttl= 72000) | ad-blocking as data, not a flag |
  | WebGUI =ssl-hsts= | HSTS header, verified from the response not the config |
  | =disablehttpredirect= **absent** | presence of the key *disables* the redirect |
  | =system/ssh/passwordauth= **absent** | presence of the key *enables* password login |
  | dnsmasq =enable= 0 | Unbound serves DNS, Kea serves DHCP; dnsmasq is a third daemon doing neither |
  | Unbound =regdhcp= / =regdhcpstatic= | DHCP and static names become resolvable as =<name>.internal= |

  *Exit codes:* =0= matches, =2= drift in audit mode, =1= something was corrected or a
  step failed. =--check= does *not* work on this playbook (the =template= task's registered
  result has no =.dest= in check mode), so =-e audit=1= is the dry run.

  *Three traps worth knowing, all hit on 2026-11-03:*

  - *=write_config()= needs =util.inc=*, and =dpinger_configure_do()= needs
    =interfaces.inc= and =system.inc=. A PHP block that only requires =config.inc= passes
    in audit mode and dies with a fatal error the first time it actually has to change
    something - which is the moment it matters.
  - *Test the write path, not just the check.* Setting the monitor IP to =8.8.8.8= and
    back is what exposed both missing includes.
  - *=dnsbl.blocklist= is the entry, not a list of entries.* Reading it as a list finds no
    =type= key and reports the blocklist missing on a router that has one.

  *Two settings are presence-based, and that inverts the usual rule:*

  =webgui.inc= tests =!isset($config['system']['webgui']['disablehttpredirect'])= - the HTTP to
  HTTPS redirect is on **only while that key does not exist**. Writing ='0'= into it disables
  the redirect and lighttpd stops listening on =:80= entirely. The same is true of
  =system/ssh/passwordauth=: the key existing means password login is *enabled*, so turning
  it off means removing the key, not setting it to ='0'=.

  Both were discovered the same way, on 2026-11-03, and both are the reason this page says to
  **verify the effect, not the stored value**: the first version of the admin block wrote
  =hsts= (a key that does not exist - the real one is =ssl-hsts=) and =redirect_http=
  (also invented). The config looked right, the audit passed, and nothing changed.

  *What is still manual:* taking a fresh config export after hand-made changes. See
  =network/exports/README.md= - the exports are SOPS-encrypted in the repo precisely
  because they cover what neither OpenTofu nor the baseline reach.

* What is still clicked

  As of 2026-11-01 the router holds **26 firewall rules and 7 aliases** that are not
  in code. The same loop applies: import them, read the first plan, and change them
  only from that point. Until then, treat a firewall change as the last thing still
  done by mouse, and write down what you clicked.
