I wanted a blog where I could just write, and I didn't want to run a database
or fight a CMS. What I ended up with is a small pipeline I mostly understand,
and I'm writing it down partly so I can remember how it fits together.

* Writing

Every post is a file in =org/=. This one starts like this:

#+begin_src org
#+TITLE: How this site is built
#+DATE: 2026-10-02
#+FILETAGS: hugo:emacs:ci

Body text in Org.
#+end_src

I use Org because I already live in Emacs, and I like that I never have to
think about HTML. I'm sure there are things I'm not using, but it gets out of
the way, which is what I want from a writing format.

* Converting

A small script turns each Org file into Hugo Markdown:

#+begin_src shell
pandoc -s -f org -t markdown --wrap=none org/post.org \
  -o content/posts/post/index.md
#+end_src

Pandoc maps =#+TITLE= and =#+DATE= into YAML front matter. I had to add one
extra step to get =#+FILETAGS= to become Hugo tags, and I'll be honest: I
mostly copied that from someone else and only half understand it.

* Building and shipping

#+begin_src shell
hugo --minify    # Org -> HTML into public/
#+end_src

CI runs the same thing on every push:

1. convert Org to Markdown
2. run =hugo --minify=
3. build a small nginx image with =public/= in it
4. push the image to GHCR and bump its tag

Then ArgoCD notices and rolls it out, same as everything else in the lab. The
part that still feels a little like magic to me is how the tag bump gets from CI
back into git so ArgoCD can see it — I set it up and it works, but it's the
piece I'd have to re-read before changing.

* Four jobs, four tools

| Job        | Tool            |
|------------+-----------------|
| writing    | Org and Emacs   |
| conversion | pandoc          |
| build      | Hugo            |
| deploy     | GHCR and ArgoCD |

I like that each tool does one thing, because it means when something breaks I
have a good idea *where* it broke. That's been more useful to me while learning
than any cleverness would have been.
