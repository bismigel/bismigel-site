I wanted somewhere to write. I didn't want to run a database or learn a whole
content system. What I ended up with is a small set of steps that I mostly
understand, and I'm writing it down so I can remember how it fits together.

* Writing

Each post is just a file with a name like =org/this-file=. This one starts like
this:

#+begin_src org
#+TITLE: How this site is built
#+DATE: 2026-10-02
#+FILETAGS: hugo:emacs:ci

Body text in Org.
#+end_src

I write in Org because I already use Emacs. It means I never have to deal with
the messy HTML underneath. There's probably a lot I'm not using. It mostly stays
out of my way, which is all I want.

* Turning it into a website

A small script turns my files into the format the website builder wants:

#+begin_src shell
pandoc -s -f org -t markdown --wrap=none org/post.org \
  -o content/posts/post/index.md
#+end_src

I had to add an extra bit so my tags show up as tags. I copied that bit from
someone else and I only half understand it. It works, so I've left it alone.

* Building and shipping

#+begin_src shell
hugo --minify    # Org -> HTML into public/
#+end_src

A robot runs the same steps every time I push:

1. turn the files into the website format
2. run the website builder
3. put the result into a small web server image
4. save the image and update the version number

Then ArgoCD sees the new version and updates the site. I never do it by hand. The
part I don't really follow is how the robot's version number gets back into my
config so ArgoCD can see it. I set it up once and it works, but I'd have to read
it again before touching it.

* Four jobs, four tools

| Job        | Tool            |
|------------+-----------------|
| writing    | Org and Emacs   |
| conversion | pandoc          |
| build      | Hugo            |
| deploy     | GHCR and ArgoCD |

I like that each tool does one job, because when something breaks I can usually
tell *where* it broke. That's been more useful to me than anything clever.
