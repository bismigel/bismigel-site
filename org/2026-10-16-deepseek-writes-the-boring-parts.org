I held off letting a model write code for longer than I should have. I think I felt
like I was supposed to be against it. But a lot of what holds this lab together is
genuinely boring — NixOS modules, Kubernetes manifests, the same small patterns in
slightly different shapes — and I was spending evenings retyping things I'd already
figured out. So I let a model do it, then spent a while finding where that was a good
idea and where it wasn't.

The same lesson showed up one level up, later, when I put an *agent* inside the lab.
This is both halves.

* Where the model earns its keep

The rule I settled on: if I can describe the shape of the answer in one sentence, I
let the model write it. A new secret that copies an existing one. A Deployment with the
same labels and probes as the rest. The tenth version of a shell script. Those aren't
problems to solve, they're typing, and I've stopped feeling I learn anything retyping
them.

Two things surprised me with how useful they were. *Cross-language translation*: I can
read a Kubernetes manifest but don't remember every field name, and I definitely don't
remember NixOS option names. Having something that does turns a guess into a build error
five minutes later instead of a subtle bug. And *the first draft of anything boring*: I'll
happily rewrite a script, but I hate writing the first one.

* Where it doesn't

It's confidently wrong about anything recent or unusual, and my whole lab is unusual.
It'll invent a Helm value, assume a default that changed two versions ago, or write a
manifest that looks fine but quietly does the wrong thing for *this* cluster, because it
has no idea what this cluster is. All three have happened to me.

So my line is: it drafts, I decide. Nothing reaches the cluster without me reading it,
and anything touching secrets, the edge, or the shape of the data is mine. I think of it
as a fast, tireless, slightly overconfident junior.

* Keeping the keys out

One rule I won't bend: the model never sees a secret. It doesn't need the value of
anything to write code that *references* it. Same for prompts — a pasted config, a token
in an error message — placeholder, never the real thing. I caught myself pasting a real
value once, and once is too many.

* Putting an agent in the cluster

Once the lab was reproducible, there was one idea I kept circling: stop being the only
one who can run it. Put an agent inside the cluster, give it my tools, let it do the
small work. Same model underneath, same lesson one level up.

It's one workload, deployed like everything else. You reach it two ways, both behind the
same login check: a web dashboard behind Cloudflare Access, and a Telegram bot that only
answers accounts I've added by hand. Nobody else gets a reply.

What makes it useful isn't the chat. The box it runs on isn't a sandbox — it has a shell
with `kubectl`, `gh`, `git`, `helm`, `jq`, and my own notes. So when I ask something, it
doesn't summarize a log I pasted; it goes and looks. That was the moment it stopped being
a toy. It's also the danger. The cleaner way to give it room is MCP servers, which hand
it a defined set of operations instead of a whole shell. I prefer them not because
they're more capable — a shell with `kubectl` can do more — but because a defined tool is
something I can name, think about, and block. A shell is a list with no end.

* The leash

Full autonomy is the easy setting and, I'm now sure, the wrong one. I want two things
from something with the run of the place: it shouldn't be able to make a change I'd be
embarrassed by, and I should still be able to send it off without watching it. Three
rules, plus limits it can't talk its way around:

- *It proposes, it doesn't commit.* It works on branches and opens pull requests, and
  the main branch is protected, so that isn't just a suggestion. The review is the whole
  point.
- *It doesn't get the Cloudflare token.* Cloudflare is the one thing that can expose the
  house, so the agent reaches it through a small proxy that holds the token and forwards
  *reads*, answering every write with a flat no. It can't change the edge, and it can't
  leak a token it never had.
- *Secrets stay in a store* and arrive as environment variables, so the agent sees the
  *name* of a credential and nothing more.

* What went wrong, and what I think now

The honest one. During setup, a job that pushed placeholder values into the secret store
on a timer kept running after I'd put the real values in. On its next tick it overwrote
them again. The agent then spent an evening being confidently useless, and I spent it
assuming the tools were broken. The tools were fine. Anything that writes to your source
of truth on a timer will eventually do it at exactly the wrong moment, and I still don't
have a good way to stop it beyond remembering.

The value is real but smaller than I imagined. The agent is good at the same things the
model is good at when it writes code: the mechanical, the repetitive, the look-it-up.
It's genuinely useful to have a box that answers "what's actually running, and is it
healthy" without me opening a terminal, and that can open the PR for the small thing it
noticed. It isn't useful for anything needing judgment, and I've stopped hoping it will
be.

The worry isn't the model being malicious. It's the model being confidently wrong at the
edge of what it can see — which is the same worry I have about myself. The answer is the
same in both cases: put the parts that can't be undone behind a human, and let everything
else move fast.
