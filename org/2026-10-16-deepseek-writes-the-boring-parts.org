For a long time I did not let a model write code for me. I think I felt I was supposed to
be against it. But a lot of this lab is boring work: NixOS modules, Kubernetes files, the
same small patterns again and again. I was spending my evenings retyping things I had
already worked out.

So I let a model do some of it, then spent time finding out where that was a good idea.
Later I saw the same lesson one step up, when I put an *agent* inside the lab.

* Where the model helps

My rule is simple: if I can describe the answer in one sentence, the model writes it. A new
secret that copies an old one. A Deployment with the same labels and checks as the others.
The tenth version of a shell script. Those are not problems to solve, they are typing.

Two things surprised me. The first is *translation between languages*: I can read a
Kubernetes file but I do not remember every field name, and I really do not remember NixOS
option names. A model does, so instead of guessing and finding out through a build error
five minutes later, I get it right the first time. The second is *the first draft of
anything boring*. I am happy to rewrite a script; I hate writing the first version.

* Where it does not help

The model is confidently wrong about anything new or unusual, and my whole lab is unusual.
It invents a Helm value. It assumes a setting that changed two versions ago. It writes a
file that looks fine and quietly does the wrong thing for *this* cluster, because it has no
idea what this cluster is. All three have happened.

So: it writes a draft, and I decide. Nothing reaches the cluster before I read it. Anything
about secrets, the edge, or the shape of my data is my job. I think of it as a fast,
tireless, slightly overconfident junior.

One rule I do not bend: the model never sees a secret. It does not need the value of
anything to write code that *uses* it, and the same goes for prompts. A config I paste or a
token inside an error message is a placeholder, never the real thing. I caught myself
pasting a real value once. Once is too many.

* Why an agent instead of another dashboard

I have five dashboards, each answering a different question. That is good when I am
debugging and bad when I just want to know whether the lab is healthy.

A dashboard waits for me to look. An alert tells me when a line is crossed. Neither
explains what it found. I wanted a first responder that could check the nodes, query
Prometheus, read a pod log, look at ArgoCD and put the result in one short message.

That is Hermes, and the dramatic name is the most dramatic part. It watches, triages and
reports. I still make the changes.

* What it does

- Every morning at 08:00 America/Toronto it checks nodes, pods, restarts, ArgoCD sync and
  health, firing alerts, filesystem use and memory trends, and sends a short report to
  Telegram.
- On request it can look at a deployment, read pod logs, query Prometheus, check ArgoCD,
  inspect the media queue, or search the book stack.
- It can open a pull request. The rule is branches and pull requests, never main.
- It can add a series or a book to the media queue; the media tools have no delete action,
  so it cannot remove anything.
- It can read Cloudflare state — tunnels, zones, DNS, certificates, Access apps — and
  cannot change any of it.

The daily report is the part that changed how I use the lab. It is not a wall of graphs,
it is a short list of what is healthy and what is not, and it lands where I already look.

* The architecture

One Deployment, with a PVC for state at =/opt/data= holding config, sessions, memory and
the cron list. It talks to the lab through MCP servers, and each server is a boundary
around a set of actions.

MCP (Model Context Protocol) is a standard way to give the agent a tool with its own
permissions. I can hand it a useful action without handing it a shell command for
everything: the Kubernetes server uses a read-only ServiceAccount, the media server has no
delete action, and the Cloudflare path is an nginx proxy that only allows GET, HEAD and
OPTIONS.

The agent still has a shell for =kubectl= and =gh=. That is the part that makes it useful
and the part that makes the guardrails matter.

* The leash

Full freedom is the easy setting, and I am now sure it is the wrong one. Two things matter
for a tool with access to the lab: it should not be able to make a change that would
embarrass me, and I should be able to send it off without watching it.

The rules are in layers, and each layer assumes the one above it may fail:

| Layer | Limit |
|-------+-------|
| Kubernetes RBAC | Read-only. Get, list and watch, with no Secrets. |
| Cloudflare proxy | GET, HEAD and OPTIONS only. Every write returns 403. |
| GitHub token | Repo-scoped. The branch and pull-request rule is a working rule, not a hard block. |
| Human review | Destructive work and merges still need me. |

The hard limits are on the cluster and the edge: the Kubernetes role cannot change
anything, and the proxy cannot send a write. Those are technical blocks, not suggestions.
The =SOUL.md= mounts the same rules in plain language — pull requests only, ask before
anything destructive, never write a secret to a file or a log — but the prompt is the last
layer, not the first.

The GitHub rule is the soft spot. A repo-scoped token can still push to main if the agent
decides to, which is why every branch and pull request gets a human look. I would rather
say that plainly than pretend the prompt is a wall.

What it cannot do, by design: apply changes to the cluster, merge its own pull requests,
write to Cloudflare, delete media or books, read Kubernetes Secrets, or replace
Alertmanager. It also cannot run outside the lab, so if the cluster is down the agent is
down — which is why the dead-man's switch lives on the workstation outside the cluster.

* The setup, which is boring on purpose

1. **Run it as a workload.** A normal Deployment with a PVC at =/opt/data=.
2. **Give it a face.** A Telegram bot with a single-user allowlist, and a dashboard behind
   Cloudflare Access plus basic auth.
3. **Give it context.** Mount the operating docs and =SOUL.md=. An agent without context is
   a confident guesser.
4. **Add MCP servers.** Kubernetes, Prometheus, media, GitHub. Each gets its own
   credentials and its own limits.
5. **Use a dedicated ServiceAccount.** A read-only ClusterRole with get, list and watch. No
   Secrets.
6. **Wrap Cloudflare.** The token sits behind a sidecar that returns 403 for every
   state-changing request; the write-capable token stays on the host, outside the pod.
7. **Scope GitHub.** A repo-scoped token, branches and pull requests as the rule, no merge
   permission.
8. **Seed a daily job.** The 08:00 report is a prompt, not a fixed script, so it can adapt
   to what it finds. Ask for a short answer and no secrets.
9. **Back up the state.** The agent's memory and job list are part of the appdata backup; a
   rebuilt agent should remember how the lab works.

The model is DeepSeek =deepseek-chat= through a custom OpenAI-compatible provider. The
model is not the interesting part. The tools and the boundaries are.

* What went wrong

While setting this up I ran a job that pushed placeholder values into the secret store on a
timer. Later I put the real values in, but the job kept running, and on its next run it
wrote the placeholders back over the real values. The agent then spent an evening being
confidently useless while I spent it thinking the tools were broken. The tools were fine.

The lesson is not about agents. Anything that writes to your source of truth on a timer
will one day do it at the worst moment. I still do not have a good way to stop that.

* Is it worth it

The value is real, but smaller than I imagined. The agent is good at the things the model
is good at: the boring, the repeated, the look-it-up. Having a box that answers "what is
running, and is it healthy" without opening a terminal is useful. So is a pull request for
a small thing it noticed. It is not useful for anything that needs judgement, and I have
stopped hoping it will be.

My worry is not that the model is bad. My worry is that it is confidently wrong at the edge
of what it can see. That is also my worry about myself, and the answer is the same: keep
the irreversible behind a human, let everything else move fast.

So the lab ran, and a model wrote a good part of it. Then I tried to watch something on it,
and hit a wall.
