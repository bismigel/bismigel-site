I resisted using a model to write code for longer than I should have. It felt
like something I was supposed to have an opinion about being against. But a lot
of what holds this lab together is genuinely dull — NixOS modules, Kubernetes
manifests, and the same small patterns in slightly different shapes over and
over — and I was spending evenings retyping things I'd already figured out. So I
let a model do it, and then spent a while working out where that was a good idea
and where it wasn't. I'm still working that out, honestly.

* What I hand it

The rough rule I settled on: if I can describe the shape of the answer in a
sentence, I let the model write it. A new ExternalSecret that mirrors an existing
one. A Deployment with the labels and probes the rest of the cluster expects. A
shell script that does a thing I've already done three times. These aren't
problems to solve; they're typing, and I've stopped feeling like I'm learning
anything by doing them myself.

The bigger the mechanical part and the smaller the judgement part, the better it
does. Renaming a field across twenty files, writing the tenth variation of a
GitHub Actions step, turning a schema into structs. It does those instantly and
correctly, whereas I'd make a typo and then hunt it down for ten minutes.

* Where it earns its keep

Two things surprised me with how useful they were. The first is
*cross-language translation*. I can read a Kubernetes manifest, but I don't
remember the exact shape of every field, and I certainly don't remember NixOS
option names. Having something that does is a real speedup, because when I get
an option name wrong the failure is a build error five minutes later, not a
subtle bug — so I can get away with not knowing, and check it the cheap way.

The second is *the first draft of anything boring*. I'll happily write the
second draft of a script; I resent the first. So I ask for a first draft, read
it, and rewrite the parts that actually matter. It gets me off the blank page,
which turns out to be most of my friction.

* Where it does not

It's confidently wrong about anything recent or niche, and my whole lab is niche.
It will invent a Helm value that doesn't exist, assume a default that changed two
versions ago, or write a perfectly reasonable manifest that quietly does the
wrong thing for *this* cluster because it has no idea what this cluster is. I've
been burned by all three, which is how I know.

So the line for me is: it drafts, I own. Nothing it writes reaches the cluster
without me reading it, and anything touching secrets, the network edge, or the
shape of the data is mine to get right. The way I think of it now is a fast,
tireless, slightly overconfident junior — useful, as long as you don't let it
merge.

* Keeping the keys out

The one rule I won't bend: the model never sees a secret. It doesn't need the
value of anything to write the code that *references* it, and the values live in
a store the code only names. I try to treat prompts the same way — a pasted
config, a log line, a token in an error message. If I need to show it something,
it's a placeholder, never the real thing. I've caught myself pasting a real value
once, and that's once too many.

* What I can actually open-source

Part of why I like this setup is that it's supposed to be reproducible, so I
periodically re-check which repos could be public. The honest answer is two
buckets.

The generic ones are fine as they are, because there's nothing personal in them:
the app template, the little test APIs, the site itself. Nothing about my
network leaks from a template full of placeholders.

The homelab repos are the interesting case. There are no secrets in them — no
keys, tokens, or passwords; everything sensitive lives in the store, and the
manifests only reference names. But they do *describe* the lab, and the lab isn't
abstract: the boxes, the private addresses, the subdomains, the ports. Making
them public wouldn't hand anyone a credential; it would hand them a map. For a
lot of homelabbers that's a fine trade, and honestly it's why the repos are
interesting to read. For me it's a decision I want to make on purpose rather than
by accident, so the sensitive ones stay private and the boring ones don't.

* The thing underneath

The agent that tends this lab, which I'll write about next, runs on the same kind
of model, and it's the same lesson one level up: the model is great at the
mechanical and unreliable at the judgement, so the whole design is about putting
the judgement somewhere it can't reach and letting it do the rest.
