For a long time, I did not let a model write code for me. I think I felt I was supposed
to be against it.

But a lot of this lab is boring work. There are NixOS modules, Kubernetes files, and
the same small patterns again and again. I was spending my evenings retyping things I
had already worked out. So I let a model do some of it, then spent time finding out
where that was a good idea and where it was not.

Later, I saw the same lesson again, one step up, when I put an *agent* inside the lab.
This post covers both parts.

* Where the model helps

My rule is simple. If I can describe the answer in one sentence, I let the model write
it. A new secret that copies an old one. A Deployment with the same labels and checks
as the others. The tenth version of a shell script. These are not problems to solve.
They are typing, and I do not learn much from typing them again.

Two things surprised me, because they helped a lot. The first is *translation between
languages*. I can read a Kubernetes file, but I do not remember every field name. And I
really do not remember NixOS option names. A model does. So instead of guessing, I get
a build error five minutes later. That is a cheap way to find out I was wrong. The
second is *the first draft of anything boring*. I am happy to rewrite a script, but I
hate writing the first version. So I ask for a draft, I read it, and I fix the parts
that matter.

* Where it does not help

The model is confidently wrong about anything new or unusual, and my whole lab is
unusual. It will invent a Helm value. It will assume a setting that changed two
versions ago. Or it will write a file that looks fine but quietly does the wrong thing
for *this* cluster, because it has no idea what this cluster is. All three have
happened to me.

So my rule is: it writes a draft, and I decide. Nothing goes to the cluster before I
read it. Anything about secrets, the edge, or the shape of my data is my job. I think
of the model as a fast, tireless, slightly overconfident junior.

* Keeping the keys out

One rule I will not bend: the model never sees a secret. It does not need the value of
anything to write code that *uses* it. The same goes for my prompts. A config I paste,
or a token inside an error message, is always a placeholder, never the real thing. I
caught myself pasting a real value once. Once is too many.

* An agent inside the cluster

Once the lab could rebuild itself, one idea kept coming back. I did not want to be the
only person who could run it. So I put an agent inside the cluster, gave it my tools,
and let it do the small work. Same model underneath. Same lesson, one step up.

It is one workload, built like everything else, and you reach it in two ways. Both sit
behind the same login check. There is a web page behind Cloudflare Access, and a
Telegram bot that only answers accounts I added by hand. Nobody else gets a reply.

The useful part is not the chat. The machine it runs on is not a sandbox. It has a
shell, with =kubectl=, =gh=, =git=, =helm=, =jq=, and my own notes. So when I ask it
something, it does not summarize a log I pasted; it goes and looks. That is when it
stopped being a toy. It is also the danger.

There is a cleaner way to give it room: MCP servers. They give it a clear list of
actions instead of a whole shell. I prefer them. Not because they can do more (a
shell with =kubectl= can do more), but because I can name each action, think about it,
and block it. A shell is a list with no end.

* The leash

Full freedom is the easy setting. I am now sure it is the wrong one. I want two things
from a tool with full access to the lab. First, it should not be able to make a change
that would embarrass me. Second, I should be able to send it off without watching it.

So I gave it three rules, plus a few limits it cannot get around:

- *It suggests, it does not commit.* It works on branches and opens pull requests. The
  main branch is protected, so that is not just a suggestion. The review is the whole
  point.
- *It does not get the Cloudflare token.* Cloudflare is the one thing that can expose
  my house. So the agent reaches it through a small proxy. The proxy holds the token
  and only passes *reads*. Every write gets a flat no. It cannot change the edge, and
  it cannot leak a token it never had.
- *Secrets stay in a store*, and arrive as environment variables. So the agent sees the
  *name* of a credential, and nothing more.

* What went wrong, and what I think now

Here is the honest part. While I set things up, I ran a job that pushed placeholder
values into the secret store on a timer. Later, I put in the real values, but the job
kept running. On its next run, it wrote the placeholders back over the real values.
The agent then spent an evening being confidently useless, and I spent that evening
thinking the tools were broken. The tools were fine.

The lesson is not about agents. It is this: anything that writes to your source of
truth on a timer will one day do it at the worst moment. I still do not have a good way
to stop that. I just remember it.

The value is real, but smaller than I imagined. The agent is good at the same things
the model is good at: the boring, the repeated, the look-it-up. It is useful to have a
box that can answer "what is running, and is it healthy" without me opening a terminal.
It is useful that it can open a pull request for a small thing it noticed. It is not
useful for anything that needs judgement, and I have stopped hoping it will be.

My worry is not that the model is bad. My worry is that it is confidently wrong at the
edge of what it can see. That is also my worry about myself. The answer is the same for
both: keep the things that cannot be undone behind a human, and let everything else
move fast.

So the lab ran, and a model wrote a good part of it. Then I tried to watch something on
it, and hit a wall.
