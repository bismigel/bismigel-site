I've been messing with this homelab for a few months and I'm not an expert at any
of it. Most of what's here I copied from guides and other people's configs, then
changed until it worked. I'm writing it down so I don't forget — this is the tour
of what it turned into, and the decisions behind it.

* The boxes

Two computers, and I didn't plan the split.

- An AMD Ryzen 5 4600G, built from leftover parts. It runs my sites and most
  everything else.
- An Intel i5-7500T, bought used for about $100, because that generation can do
  QuickSync — hardware video transcoding. It runs the media stack.

Later a third turned up: a 2012 MacBook Pro under a pile of cables. It only helps
the cluster agree and runs nothing itself. That's a later post.

* NixOS

I started on Proxmox, didn't like the extra layer between me and the thing I
wanted to change, and wiped it to put the OS straight on the hardware.

I picked NixOS because I kept forgetting what I'd done. Now the whole machine is
one file I can read back. I still find the language hard and copy a lot of it, but
being able to rebuild a box from that file is why I stayed.

nix run github:serokell/deploy-rs -- .#<host>
#+end_src

* One cluster, not two

This is the part I got wrong first. I started with two separate single-node
clusters, one per box, each with its own copy of everything. Then I read that a
single-node cluster is one machine, and a two-node one is actually *worse* than
either — the cluster's memory needs a majority to agree, and with two you lose the
majority the moment either dies.

So I merged them into one cluster of three machines. The MacBook was just enough to
tolerate losing one. "More machines" and "one cluster" are different ideas, and I'd
confused them. The merge is its own post later.

* Where things run

The media stack is pinned to the Intel box, because it's the one with QuickSync and
it'd be a waste anywhere else. Everything else lives on the AMD box. The MacBook is
kept deliberately small — tainted so nothing lands on it. Written down it looks
obvious; it took me a while.

* Kubernetes

Honestly, plain Docker would have worked. I picked Kubernetes to learn it, and I
don't know it well. Each box runs k3s. I turned off the two extras it ships with
(Traefik and a load balancer) because I didn't understand them, and used
ingress-nginx instead, which I could follow. Maybe the wrong call; it's one I can
read.

* ArgoCD

The cluster's desired state lives in git and ArgoCD makes the cluster match it. I
understand it at a high level. One ArgoCD runs *inside* the cluster and manages the
whole thing — I can't tell you what happens if it breaks, which is part of why the
control plane and the storage have backups.

The layout looks like this:

#+begin_example
bakuran-gitops/
  bootstrap/root-app.yaml       # the one root
  applications/<cluster>/...    # one folder per cluster
  manifests/<app>/...           # raw manifests the apps point at
#+end_example

There's a clever bit that picks up new machines automatically. I copied it from an
example and couldn't explain exactly how it works.

When I change an app:

1. I push the code.
2. A robot builds it and pushes a container image.
3. The robot opens a pull request that bumps one version number.
4. ArgoCD notices the merge and updates the running app.

I like this because the robot never gets the keys to my cluster — it can only
change one number, and I approve it.

* Secrets

Short version: plaintext never enters git. Host secrets (like the tunnel
credentials) stay encrypted in the NixOS repo with SOPS; cluster secrets live
outside the lab in Bitwarden and get injected by External Secrets Operator. I went
through two worse setups first — that's the post after next.

* The front door

Nothing is exposed directly. A tunnel makes an outgoing connection to Cloudflare,
and that's how the outside reaches my sites. Access sits in front of it, so a
request has to belong to someone first. I understand this part the least and trust
it the most.

* What I'd still change

The front door trusts an identity header Access adds, which is only safe if the
origin can be reached *only* through the tunnel. For a while the services were also
reachable on the LAN, where that header can be faked. I fixed that since — the LAN
can't bypass the edge anymore — but I'd rather leave it written down than pretend
it was never a problem.

Which is the theme: I've gotten more from the things I got wrong than from anything
I read.
