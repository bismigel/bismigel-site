I have run this homelab for a few months. It is not a production platform, but it is
built like one: declarative hosts, one GitOps control plane, a three-node etcd
quorum, and a small Cloudflare edge.

I am a traditional sysadmin. Linux, networking and observability are the familiar
parts. Kubernetes, GitOps and the cloud-native tooling are what I am learning here.
This post is the design and the trade-offs behind it.

* The computers

I have two computers. I did not plan how to split the work between them.

- The first is an AMD Ryzen 5 4600G. I built it from spare parts. It runs my sites
  and almost everything else.
- The second is an Intel i5-7500T. I bought it used for about $100. I chose it
  because this CPU supports QuickSync. QuickSync means it can convert video in
  hardware. It runs the media apps.

  Later, a third machine turned up: a 2012 MacBook Pro I found under a pile of
  cables. At that point it only helped the cluster stay alive and did not run any
  apps. I write about it in a later post.

  *Update 2026-10-20:* the MacBook now runs Immich and one Redis HA replica. The
  taint remains, and both workloads opt in with explicit tolerations.

* NixOS

I started with Proxmox. I did not like the extra layer between me and the thing I
wanted to change. So I removed it, and put the operating system directly on the
hardware.

I chose NixOS because I wanted the host state to be reviewable and reproducible.
The machine is a set of declarative modules, and a rebuild produces the same
system. The module language still sends me to the manual, but the state is not
hidden in shell history.

#+begin_src shell
nix run github:serokell/deploy-rs -- .#<host>
#+end_src

* One cluster, not two

This is the first thing I got wrong. At the start, I had two separate clusters.
Each box was its own cluster of one machine, with its own copy of everything.

Then I learned something. A cluster of one machine is just one machine. And a
cluster of two machines is *worse* than either. Here is why. The cluster keeps its
memory on all its machines, and to change anything, most of them must agree. With
two machines, you need both. So if one dies, the whole cluster stops. Two machines
are not better than one. They are worse.

So I joined the two machines into one cluster. Later I added the MacBook as a third
machine. Three is enough to lose one machine and keep going. "More machines" and
"one cluster" are two different ideas, and I had mixed them up. The merge has its
own post later.

* Where things run

The media apps run only on the Intel box. That box has QuickSync, so it is the right
place for them. Every other app runs on the AMD box. I keep the MacBook small on
purpose. I marked it so that no apps can land on it.

When I write it down, it looks obvious. It took me a while to get there.

* Kubernetes

Plain Docker would have run these services. I chose Kubernetes because I wanted one
scheduler, one GitOps surface and one place to reason about health. Kubernetes is
the part I am still learning, and the lab is small enough that I can see the whole
control plane.

Each box runs k3s. k3s ships Traefik and ServiceLB; I disabled both and run
ingress-nginx. That is not a judgement on Traefik. It is one ingress controller with
explicit config, and I can trace a request through it.

* ArgoCD

The desired state lives in git. One in-cluster ArgoCD reconciles it. GitOps was the
biggest mental shift for me: the cluster pulls toward git, instead of me pushing
commands at it. The failure mode is a control-plane outage, which is why the hosts
are rebuildable, app state goes to R2, and the cluster config lives in git.

The layout looks like this:

#+begin_example
bakuran-gitops/
  bootstrap/root-app.yaml       # the one root
  applications/<cluster>/...    # one folder per cluster
  manifests/<app>/...           # the files the apps point at
#+end_example

The root Application points at the =applications/= tree. A second ApplicationSet
generates the per-node exporters, so a new node is picked up without a manual
registration.

When I change an app:

1. I push to the app repo's =main=.
2. GitHub Actions builds the image and pushes it to GHCR with an immutable tag
   (=main-<UTC timestamp>-<sha>=).
3. The workflow rewrites the image tag in the Kubernetes manifest, pushes a branch
   and opens a pull request.
4. ArgoCD reconciles the merged commit and rolls the Deployment.

The CI side is familiar. The part I had to learn is the handoff: CI writes only an
image tag to git, and ArgoCD owns the cluster. The workflow has =contents: write=
and =packages: write=, and no kubeconfig. This site auto-merges the tag PR; the app
template pushes the bump directly. Either way, the manifest is the only interface
between CI and the cluster.

* Secrets

Plain text never goes into git. Host secrets (tunnel credentials, keys) are
SOPS-encrypted with age in the NixOS repo. Cluster secrets live in Bitwarden
Secrets Manager and are materialised by External Secrets Operator. I tried two
worse setups first; that is the post after next.

* The front door

Nothing is published directly. =cloudflared= makes outbound connections to
Cloudflare, and the tunnel routes hostnames to the in-cluster ingress. Access
authenticates the admin surfaces; public apps use their own auth. The origin is
reachable only through the tunnel, which is what makes the Access identity header
trustworthy.

* What I would still change

The front door trusts an identity header that Access adds. That is only safe if the
origin can be reached *only* through the tunnel. For a while, my services were also
reachable on the LAN. On the LAN, someone could fake that header. I fixed this later.
The LAN can no longer bypass the edge. But I want to keep it written down, instead of
pretending it was never a problem.

That is the theme, really. I have learned more from the things I got wrong than from
anything I read.
