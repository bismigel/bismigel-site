I have worked on this homelab for a few months. I am not an expert at any of it.
Most of it I copied from guides and other people's configs, then changed until it
worked. I am writing it down so I do not forget it.

This post is a tour of what the lab became, and why I made the choices I did.

* The computers

I have two computers. I did not plan how to split the work between them.

- The first is an AMD Ryzen 5 4600G. I built it from spare parts. It runs my sites
  and almost everything else.
- The second is an Intel i5-7500T. I bought it used for about $100. I chose it
  because this CPU supports QuickSync. QuickSync means it can convert video in
  hardware. It runs the media apps.

Later, a third machine turned up: a 2012 MacBook Pro I found under a pile of
cables. It only helps the cluster stay alive and does not run any apps. I write
about it in a later post.

* NixOS

I started with Proxmox. I did not like the extra layer between me and the thing I
wanted to change. So I removed it, and put the operating system directly on the
hardware.

I chose NixOS because I kept forgetting what I had done to my machines. Now the
whole machine is one file I can read back. The language is still hard for me, and
I copy a lot of it. But this is why I stayed: I can rebuild a machine from that
one file.

#+begin_src shell
nix run github:serokell/deploy-rs -- .#<host>
#+end_src

* One cluster, not two

This is the first thing I got wrong. At the start, I had two separate clusters.
Each box was its own cluster of one machine, with its own copy of everything.

Then I learned something. A cluster of one machine is just one machine. And a
cluster of two machines is *worse* than either. Here is why. The cluster keeps its
memory on all its machines, and to change anything, most of them must agree. With
two machines, you need both. So if one dies, the whole cluster stops. Two machines
are not better than one. They are worse.

So I joined the two machines into one cluster. Later I added the MacBook as a third
machine. Three is enough to lose one machine and keep going. "More machines" and
"one cluster" are two different ideas, and I had mixed them up. The merge has its
own post later.

* Where things run

The media apps run only on the Intel box. That box has QuickSync, so it is the right
place for them. Every other app runs on the AMD box. I keep the MacBook small on
purpose. I marked it so that no apps can land on it.

When I write it down, it looks obvious. It took me a while to get there.

* Kubernetes

To be honest, plain Docker would have worked fine. I chose Kubernetes because I
wanted to learn it. I still do not know it well.

Each box runs k3s. k3s comes with two extra parts (Traefik and a load balancer). I
did not understand them, so I turned them off. I used ingress-nginx instead, because
I could follow what it does. Maybe that was the wrong choice. But it is a choice I
can read.

* ArgoCD

The state I want for the cluster lives in git. ArgoCD makes the cluster match it. I
understand it at a high level. One ArgoCD runs *inside* the cluster and manages the
whole thing. I cannot tell you what happens if it breaks. That is one reason the
control plane and the storage have backups.

The layout looks like this:

#+begin_example
bakuran-gitops/
  bootstrap/root-app.yaml       # the one root
  applications/<cluster>/...    # one folder per cluster
  manifests/<app>/...           # the files the apps point at
#+end_example

One part is clever: it finds new machines on its own. I copied it from an example. I
cannot fully explain how it works.

When I change an app, this happens:

1. I push the code.
2. A robot builds it and pushes a container image.
3. The robot opens a pull request that changes one version number.
4. ArgoCD sees the merge and updates the running app.

I like this. The robot never gets the keys to my cluster. It can only change one
number, and I approve the change.

* Secrets

The short version: plain text never goes into git. Secrets for the machines (like the
tunnel credentials) stay encrypted in the NixOS repo. I use a tool called SOPS for
that. Secrets for the cluster live outside the lab, in Bitwarden. A tool called
External Secrets Operator puts them into the cluster. I tried two worse setups first.
That is the post after next.

* The front door

Nothing is open to the internet directly. A tunnel makes an outgoing connection to
Cloudflare. That is how the outside world reaches my sites. Access sits in front of
it. So a request must belong to someone before it gets in. I understand this part the
least, and I trust it the most.

* What I would still change

The front door trusts an identity header that Access adds. That is only safe if the
origin can be reached *only* through the tunnel. For a while, my services were also
reachable on the LAN. On the LAN, someone could fake that header. I fixed this later.
The LAN can no longer bypass the edge. But I want to keep it written down, instead of
pretending it was never a problem.

That is the theme, really. I have learned more from the things I got wrong than from
anything I read.

Before any of the rest, I needed somewhere to write it all down. That is the next part.
