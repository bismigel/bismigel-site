#+TITLE: The design of the homelab
#+DATE: 2026-09-15
#+FILETAGS: homelab:design:nixos

I finally have the homelab shaped the way I want, so this first post is a tour of
how it's put together and *why* the pieces are where they are.

* Two machines, two jobs

There are two physical boxes:

- The *hosting box*: an AMD Ryzen 5 4600G (6c/12t). Leftover parts from my old
  PC after I dropped in a 4600G (better perf-per-watt, bless AM4). It serves the
  websites, runs the cluster's platform pieces, and hosts whatever I want to
  experiment with.

- The *media box*: an Intel i5-7500T, bought for $100 off Marketplace. This
  generation has QuickSync, so it does hardware transcoding. It runs my whole
  media stack.

The split is deliberate, not accidental. The 4600G has more cores, which suits
general apps and experimentation; the 7500T's QuickSync is wasted on anything
that is not media. So the entire media stack lives on the Intel box and
everything else lives on the AMD box.

* Everything is NixOS

Initially this was deployed in proxmox lxc but i didnt like the additional layer that I have to work with before getting to the container.
Using baremetal will remove that layer. I chose nixos specifically for the ease of configuration and avoiding drift from spec.

Both run NixOS, declared in a single flake. The OS is code: hosts, modules, disko
disk layouts, and a =deploy-rs= hook so I can push a rebuild over SSH:

#+begin_src shell
nix run github:serokell/deploy-rs -- .#<host>
#+end_src

There is no half-configured box drifting over time. If I need to rebuild a
machine, I reinstall from the same flake and I am back to a known state.

* Kubernetes, but boring

This would have worked with just docker instead of a single node k3s but I specifically chose this in order
to experiment and troubleshoot and experience managing a kubernetes architecture. This would also mean I can
use existing gitops tools like Flux and ArgoCd instead of having something like an ansible job that deploys to servers.

Each box runs a single-node ~k3s~. I disabled Traefik and the built-in service
load balancer on purpose and use *ingress-nginx* instead, so ingress is explicit
rather than magic. It only runs where it earns its keep: the hosting box behind
the tunnel. The media box needs no ingress — it is reached by its own NodePorts
on the LAN.

* GitOps with ArgoCD

Cluster state lives in git and *ArgoCD* reconciles it. One repo
(~bakuran-gitops~) is the source of truth.

The part I am happiest with: there is a *single ArgoCD control plane*, and it
lives on the hosting box. It manages *both* clusters — the hosting box
in-cluster, and the media box registered as an *external cluster*. I do not run a
second ArgoCD on the media box, and I do not copy repo credentials between them.

The repo is one app-of-apps root pointing at a folder of =Application=
definitions, split per cluster, plus an =ApplicationSet= for anything that should
run everywhere:

#+begin_example
bakuran-gitops/
  bootstrap/root-app.yaml       # the one root
  clusters/                     # cluster registrations
  applications/
    <cluster>/...               # one folder per cluster
    node-exporter-appset.yaml   # shared -> every cluster
  manifests/<app>/...           # raw manifests the apps point at
#+end_example

The shared bits use an =ApplicationSet= with a *cluster generator*: it enumerates
the clusters ArgoCD knows about, so registering a new cluster enrolls it
automatically instead of duplicating manifests.

I still do not run deploys from CI:

1. I push application code.
2. CI builds a container image and pushes it to GHCR.
3. CI bumps the image tag in the manifests.
4. ArgoCD notices and rolls it out — on whichever cluster the app targets.

CI never holds cluster credentials. It only pushes a tag. That is the whole
trick, and it is why a compromised build cannot touch the cluster.

* Applications are reproducible

Every app repo ships a =deploy/k8s/= folder (Deployment, Service, Ingress) and a
GitHub Actions workflow that builds and pushes its image. To start something new
I use ~homelab-app-template~, which wires all of that up. I just write the app.

* The edge is one Cloudflare tunnel

Nothing is port-forwarded. A single ~cloudflared~ tunnel connects out to
Cloudflare, and public hostnames (like this one) route to ~ingress-nginx~ on the
hosting box. TLS terminates at Cloudflare.

* Secrets

Cluster secrets are *Sealed Secrets*: encrypted in git, decrypted by a controller
in the cluster. Host level secrets, such as the tunnel credentials, are
*SOPS*/age encrypted in the NixOS repo and decrypted at activation, keyed off each
machine's SSH host key.

(Since writing this I moved the cluster half to a managed secret store, and put
the two clusters under one control plane. The reasoning is in
[[file:2026-10-11-choosing-the-architecture.org][Choosing the architecture]].)

* What it looks like end to end

#+begin_example
push -> CI (build + push image + bump tag) -> ArgoCD -> both clusters
                                                      -> ingress-nginx
                                                      -> cloudflared -> internet
#+end_example

* Where it went next

That was the design at the start. A few decisions changed after living with it:
how the two clusters are managed, where secrets live, and how you log in. I wrote
the reasoning up separately in
