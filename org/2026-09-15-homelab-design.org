I've been messing around with this homelab for a few months. I am not an expert
at any of it. Most of what's here I copied from guides and other people's configs
and then changed bits until it worked. I'm writing it down so I don't forget, and
in case it helps someone else who's also just trying to make it work.

* Two machines

I have two computers.

- The first is an AMD Ryzen 5 4600G. These were the parts left over from my old
  PC. I read online that this CPU was good for home servers, so it became the one
  that runs my websites and most of the other stuff.

- The second is an Intel i5-7500T. I bought it used for about $100. I got this
  one on purpose because I read that this generation of Intel can do something
  called QuickSync, which is supposed to help with video. I still don't fully
  understand how that works.

I didn't sit down and plan the split between the two. It just kind of happened.
The Intel one seemed like it would be a waste on normal things, so the video
stuff went there. Maybe that's obvious and maybe it isn't. It's what I did.

* NixOS

I started out running everything in Proxmox containers. I didn't like it. There
was always an extra thing in my way before I could get to the thing I actually
wanted to change. So I wiped it and put the operating system straight on the
hardware.

I picked NixOS because I kept forgetting what I'd done to my machines. I'd set
something up, not write it down, and then have no idea how to do it again. NixOS
puts the whole machine in one file that I can look back at. I still find the
NixOS language hard and I copy a lot of it. But being able to redo a machine from
that file is the reason I stuck with it.

#+begin_src shell
nix run github:serokell/deploy-rs -- .#<host>
#+end_src

* Kubernetes

If I'm honest, I could have just used plain Docker and it would have worked fine.
Part of why I went with Kubernetes is that I wanted to learn it. I figured if it
broke I'd learn something. I don't know it very well yet.

So each machine runs a small thing called k3s. When I set it up there were two
extra pieces turned on by default, Traefik and something for load balancing. I
didn't understand what either of them did, so I turned them off and used
ingress-nginx instead, because I could follow what it was doing. Maybe that's the
wrong choice. It's the one I could understand.

I only put that ingress thing on the machine that needs it. The other machine
just gets reached directly.

* ArgoCD

I keep the setup for my cluster in a git repository, and a tool called ArgoCD
tries to make the cluster look like what's in git. I only really understand it at
a high level.

The part I'm most proud of, and also least sure about: I run one ArgoCD, on the
first machine, and it manages *both* machines. I read that you're supposed to run
one per machine, but that sounded like twice the work, so I tried it the other
way. It works so far. I could not tell you what happens if it breaks.

Everything lives in folders like this:

#+begin_example
bakuran-gitops/
  bootstrap/root-app.yaml       # the one root
  clusters/                     # cluster registrations
  applications/
    <cluster>/...               # one folder per cluster
    node-exporter-appset.yaml   # shared -> every cluster
  manifests/<app>/...           # raw manifests the apps point at
#+end_example

There's a clever bit that picks up new machines automatically. I copied it from
an example and it does what I want. I couldn't explain exactly how.

When I change an app:

1. I push the code.
2. A robot builds it and puts it in a storage place.
3. The robot edits the version number in my config.
4. ArgoCD notices and updates the running app.

I like this because the robot never gets the keys to my cluster. It can only
change one number. I'm sure there are things wrong with it that I don't know
about.

* Apps

Every app has a little folder with the files that tell Kubernetes how to run it,
plus a robot that builds the app into a picture of a container. I have a starter
template so I don't have to write the boring parts again. I usually just write
the app part. That's the part I find fun.

* The internet part

Nothing on my machines is opened up to the internet directly. A program called
cloudflared makes an outgoing connection to Cloudflare, and that's how the
outside world reaches my websites. I understand this part the least, and oddly I
trust it the most. I'll probably write more about it if it ever breaks.

* Secrets

This is passwords and keys. My first try used something called Sealed Secrets. I
picked it because other people used it, not because I understood it. Host
passwords use something called SOPS.

(I've since changed the cluster half to a different thing. I wrote about that in
[[file:2026-10-11-choosing-the-architecture.org][Choosing the architecture]],
mostly because I'm still not sure the new way is right either.)
