Two things broke my media box in the same week, and it took me a while to see they
were the same problem. One was the GPU: the pod could see the graphics device but
couldn't use it. The other was subtitles: the file had them, the player refused
them, and the stream died. In both cases the thing was *there* but not *usable*,
and the difference was one setting in a place I wasn't looking. I only figured
that out afterwards.

These are my notes on both, mostly so I don't have to work them out twice.

* Part one: give the pod the GPU

The media box has an Intel i5 with a built-in GPU. As far as I can tell, the only
real reason it earns its place is QuickSync: it can transcode video in hardware,
so a Jellyfin stream should cost a few percent of the GPU instead of a whole CPU.
I'm taking that on faith a bit, but it's why I bought this box.

On the host everything *looks* ready. The kernel driver is loaded and the device
nodes exist.

#+begin_src shell
$ ls -l /dev/dri
crw-rw---- 1 root video 226,   0 card0
crw-rw-rw- 1 root render 226, 128 renderD128
#+end_src

So the obvious move is the one every guide gives you: mount /dev/dri into the pod
and call it done.

#+begin_src yaml
volumeMounts:
  - name: dri
    mountPath: /dev/dri
volumes:
  - name: dri
    hostPath:
      path: /dev/dri
      type: Directory
#+end_src

The device shows up inside the pod. And then the transcode runs on the CPU anyway.
ffmpeg pins a core and a half, and the VAAPI driver in the logs just says it can't
find a display:

#+begin_src shell
No VA display found for device /dev/dri/renderD128
#+end_src

For a while I assumed that message meant what it said and went looking at
drivers. It doesn't. The device is there. The drivers are there. The real problem
is that *seeing a device isn't the same as being allowed to open it*. The thing
doing the allowing is the device cgroup, not the file permissions. A hostPath
mount puts the node inside the container's filesystem. It does nothing to the
container's device access list. So the open comes back EPERM, the driver reports
"no display", and you go hunting in the wrong place. That took me an
embarrassingly long time to figure out.

I proved it to myself the cheap way, just by opening the node:

#+begin_src shell
# on the host
$ ( exec 3<>/dev/dri/renderD128 && echo OK )
OK

# inside the pod
$ ( exec 3<>/dev/dri/renderD128 && echo OK )
sh: cannot create /dev/dri/renderD128: Operation not permitted
#+end_src

Open on the host, denied in the pod. That one line was the whole diagnosis for me.

** The fix

There are two ways to hand the device to the container. The blunt one is to run
the pod privileged:

#+begin_src yaml
containers:
  - name: jellyfin
    securityContext:
      privileged: true
#+end_src

That grants every host device, which is more than the GPU and more than I'd like.
But on a single-purpose media box it's the one-line answer, and it worked
immediately. The tidier option is the Intel GPU device plugin, which registers the
device as something you can request, so you ask for exactly it:

#+begin_src yaml
resources:
  limits:
    gpu.intel.com/i915: 1
#+end_src

I went privileged first just to get it working and told myself I'd switch later. I
haven't yet. I'm not sure that's the right call, and I'd rather say so than write
it up like it was a decision.

That was only half of it, because the container was never the only gate. Jellyfin
also has to be *told* to use the hardware, and by default it isn't. The encoding
settings need a hardware acceleration type:

#+begin_src json
{ "HardwareAccelerationType": "qsv",
  "VaapiDevice": "/dev/dri/renderD128",
  "EnableHardwareEncoding": true }
#+end_src

Then I checked the chain actually works instead of trusting a checkbox. The
bundled ffmpeg has the QSV encoders, and the driver opens cleanly:

#+begin_src shell
$ ffmpeg -init_hw_device qsv=hw:/dev/dri/renderD128 ... -c:v h264_qsv -f null -
libva info: va_openDriver() returns 0
#+end_src

=returns 0= was the sentence I wanted to see. After that a transcode shows up with
the right arguments and the CPU stops being the bottleneck:

#+begin_src shell
-init_hw_device vaapi=va:...,driver=iHD
-init_hw_device qsv=qs@va
-codec:v:0 h264_qsv
#+end_src

One more detail that cost me half a confused hour. The VAAPI drivers in the
official Jellyfin image don't live in the system path. If you test by hand, you
have to point at them yourself. Otherwise you get the same misleading "no display"
error and think the fix didn't work.

#+begin_src shell
LIBVA_DRIVERS_PATH=/usr/lib/jellyfin-ffmpeg/lib/dri \
LIBVA_DRIVER_NAME=iHD ffmpeg ...
#+end_src

Jellyfin does that for you when it spawns its own ffmpeg. You only need to
remember it when *you're* the one doing the spawn.

* Part two: the subtitle trap

With transcoding finally cheap, I played an episode and hit the next wall. The
moment I turned subtitles on, the player said they weren't supported and dropped
the stream. I was genuinely confused, because I could *see* the subtitles were in
the file.

They were. There were four of them, all English. The trouble was what kind they
were:

#+begin_src shell
$ ffprobe -select_streams s -show_entries stream=codec_name ...
codec_name=hdmv_pgs_subtitle
codec_name=hdmv_pgs_subtitle
#+end_src

PGS is an *image* format: each subtitle is a bitmap, not text. A browser can't
draw that as a soft subtitle. The only way to show it is to burn it into the
video, frame by frame, on the CPU, which is exactly the cost I'd just spent an
afternoon removing. Worse, a web player that knows it can't render the stream
sometimes doesn't fall back to burning it in at all. It just refuses.

The fix isn't to fight the image format. It's to add the text one. An external SRT
is a soft subtitle, the browser draws it natively, and playback stays a remux.
That's a job for Bazarr, which was already running and, it turned out, had never
downloaded anything, because I'd never set it up.

** The pitfalls, in the order I hit them

Setting up Bazarr looked like a form to fill in. It was a small obstacle course,
and each failure taught me something I would have had to learn eventually.

1. *It couldn't reach Sonarr.* The error was =Bad Request - Invalid Hostname=.
   That isn't about connecting; it's about the =Host= header. The *arr apps only
   answer to hostnames on their allow-list, and the service name Bazarr was using
   wasn't on it. It's obvious looking back, but the message says nothing about the
   *arr config.

2. *Its settings API silently ignores you.* Posting a neat JSON blob returned a
   success code and changed nothing. The endpoint doesn't take a blob. It takes
   individual form fields, dash-joined, one per setting. This is the one that
   taught me a 204 isn't proof anything happened.

3. *A default profile breaks the database.* Setting a default language profile
   made every new series fail to insert with =FOREIGN KEY constraint failed=. The
   workaround is to leave the default unset and assign the profile directly. It's
   a bug in this Bazarr build, but the workaround is small enough to live with.

4. *It thought there was nothing to do.* With the connection working and the
   provider logged in, the search found nothing, because Bazarr counts the
   *embedded* subtitles as already covering the language. The file did have
   English subtitles, after all. They were just the PGS ones the browser can't
   use. So the fix was to tell it to ignore the embedded and image-based tracks,
   so it would treat English as genuinely missing. Then it fetched SRTs, and they
   landed next to the files.

This was the same lesson as the GPU, and I didn't see it the first time. "The file
has subtitles" and "the player can use the subtitles" are two different things.
The software will happily say the first is true while failing the second.

** What it bought

An SRT next to the file makes the whole chain cheap. The stream is no longer
transcoded to burn in bitmaps. It's remuxed, the soft subtitle rides alongside,
and the CPU goes back to sleep. The same episode that wanted three cores and a
software overlay now barely registers.

So both halves ended the same way: a device that was there but not allowed, and a
subtitle that was there but couldn't be shown. Each one was fixed by finding the
single gate that actually mattered. The GPU is now usable, the subtitles are text,
and the box is quiet again.
