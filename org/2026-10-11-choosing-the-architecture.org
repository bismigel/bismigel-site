I already wrote a tour of the homelab. This one is more honest: it's the
decisions behind it, including the ones I made, unmade, and made again after
actually living with them for a while and finding out I was wrong.

* One control plane, or two

The first thing I had to decide was how to manage two separate single-node
clusters. I assumed the obvious answer was an ArgoCD on each box. It works, but
it meant two control planes to babysit, two sets of repo credentials to keep in
sync, and no single place to see the whole lab — and I knew I'd get them out of
step almost immediately.

So I tried the other way: *one* ArgoCD, on the hosting box, managing *both*
clusters, with the media box registered as an external cluster. An app just says
which cluster it belongs to:

#+begin_src yaml
destination:
  name: calamansi-intel   # or in-cluster for the hosting box
#+end_src

I'm not going to pretend I understood all the implications when I did this. I
found out afterwards that the cost is the control plane being a single blast
radius, and the win is that there is exactly one place the desired state lives.
The win is worth it to me right now; ask me again after the first time the
control plane is what breaks.

* Where each thing runs

I split the apps deliberately, though "deliberately" is doing some work there —
it was more that I couldn't justify putting a transcoding job anywhere but the
box with QuickSync. The media stack lives on the Intel box, and everything else
(lives on the AMD box). It's not just tidiness: the Intel chip earns its place
by transcoding, and the Ryzen earns its place by running everything else. It's
the kind of thing that looks obvious written down and took me a while to land
on.

* Secrets: it took three tries

This is the part I'm most embarrassed about, and the most useful to write down.
I went through three setups before landing on one I trust:

1. *SOPS with age* for host secrets. Clean, keyed off each machine's SSH host
   key, no extra service. This one stuck.
2. *Sealed Secrets* for cluster secrets. Encrypted in git, decrypted in-cluster.
   It seemed clever until I had two clusters: each has its own sealing key, so
   every secret had to be sealed per cluster, and losing a cluster lost its key.
   I'd picked it by copying, without thinking about the second cluster.
3. *Bitwarden Secrets Manager with External Secrets Operator*. The store is
   *outside* the lab, so a cluster wipe does not lose it. Rotating a credential
   is editing it in Bitwarden, not re-sealing a blob. This is the one I'd start
   with if I did it again, which is a sentence I hate writing.

* Being able to rebuild it

The test I kept asking myself was blunt, and I resisted it for a while because I
suspected I'd fail it: if both boxes die tomorrow, what do I actually need to
have kept?

The answer turned out to be smaller than I feared. Everything declarative (the
OS flake, the cluster state, the app manifests) is in git. Everything secret is
in Bitwarden. The only things that are neither are the *keys to those two
things*, so I back those up: the host SSH keys, the kubeconfig, the Bitwarden
machine token, encrypted and pushed to object storage on a timer. I'm not sure
it's a *good* backup strategy yet — I haven't tested a restore end to end — but
it's a written-down sequence instead of an archaeology project.

* Identity and the front door

The tunnel is the only way in, and Cloudflare Access sits in front of it, so a
request has to be *someone* before it reaches an app. Where an app can consume
the identity Access passes along, I let it, so each person gets their own
account. Where it cannot — the download clients, mostly — it's one shared login.
I arrived at that hybrid less by design than by hitting walls, but it's honest
about the tools.

* What I would still change

The current front door trusts the identity header Access injects. I only
realised later that this is safe *only* if the origin is reachable *only* through
the tunnel, and right now the services are also reachable on the LAN — so the
header can be forged there. I haven't fixed it, and I wouldn't call the lab
hardened until I do. This is the kind of thing I'd rather write down than
quietly leave, because I'll forget.

The whole thing is a work in progress, which is sort of the point. The property
I was actually after is that each layer is replaceable: the OS, the cluster, the
secrets, the edge. I'm finding that swapping any one of them doesn't require
touching the rest, and every time I've had to do that, it's taught me more than
reading about it did.
