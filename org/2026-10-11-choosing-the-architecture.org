I already wrote a tour of the homelab. This one is about the decisions behind it.
Some I made and kept, some I made and undid, and some I made again after living
with them for a while and finding out I was wrong.

* One control plane, or two

The first thing I had to decide was how to manage two separate single-node
clusters. I thought the obvious answer was one ArgoCD on each box. That works, but
it means two control planes to look after, two sets of git credentials to keep in
sync, and no one place to see the whole lab. I knew I'd get them out of step
almost right away.

So I tried the other way: *one* ArgoCD, on the hosting box, managing *both*
clusters, with the media box registered as an external cluster. An app just says
which cluster it belongs to:

#+begin_src yaml
destination:
  name: calamansi-intel   # or in-cluster for the hosting box
#+end_src

I'm not going to pretend I understood what I was doing. I found out later that
the downside is that if the control plane breaks, both clusters go with it. The
upside is that there's only one place the desired state lives. That's worth it to
me right now. Ask me again after the first time the control plane is the thing
that breaks.

* Where each thing runs

I split the apps between the two boxes, but I can't really call it a plan. It was
more that I couldn't see any reason to put a transcoding job on anything but the
box with QuickSync. So the media stack lives on the Intel box, and everything else
lives on the AMD box. The Intel chip earns its place by transcoding, and the Ryzen
earns its place by running everything else. It looks obvious written down, but it
took me a while to get there.

* Secrets: it took three tries

This is the part I'm most embarrassed about, and the most useful to write down. I
went through three setups before landing on one I trust:

1. *SOPS with age* for host secrets. It's simple, it uses each machine's own SSH
   host key, and there's no extra service to run. I kept this one.
2. *Sealed Secrets* for cluster secrets. They're encrypted in git and decrypted
   in the cluster. It seemed clever until I got a second cluster: each has its own
   sealing key, so I had to seal every secret again for the second cluster, and
   losing a cluster meant losing its key. I picked this one by copying what other
   people did, without thinking about there being a second cluster.
3. *Bitwarden Secrets Manager with External Secrets Operator*. The store is
   *outside* the lab, so wiping a cluster doesn't lose it. To change a password I
   edit it in Bitwarden instead of re-sealing something. If I did it again, this
   is what I'd start with. I don't love admitting that.

* Being able to rebuild it

The question I kept asking myself was simple, and I put off answering it because I
thought I'd fail: if both boxes die tomorrow, what do I actually need to still
have?

The answer was smaller than I feared. Everything declarative (the OS flake, the
cluster state, the app manifests) is in git. Everything secret is in Bitwarden.
The only things that are neither are the *keys to those two places*. So I back
those up: the host SSH keys, the kubeconfig, the Bitwarden machine token. They get
encrypted and pushed to object storage on a timer. I wouldn't call it a good
backup plan yet, because I haven't tested a restore from start to finish. At least
it's written down, instead of something I'd have to figure out later.

* Identity and the front door

The tunnel is the only way in, and Cloudflare Access sits in front of it, so a
request has to belong to someone before it reaches an app. If an app can use the
identity that Access passes along, I let it, so each person gets their own
account. If it can't (mostly the download clients), it's one shared login. I
didn't plan this mix; I got here by running into walls. It's what the tools could
do.

* What I would still change

The current front door trusts the identity header that Access adds. I only figured
out later that this is safe only if the origin can be reached only through the
tunnel. Right now the services can also be reached on the LAN, so the header can
be faked there. I haven't fixed it. I wouldn't call the lab secure until I do. I'd
rather write this down than leave it unsaid, because I'll forget.

The whole thing is unfinished, which is kind of the point. What I really wanted is
for each layer to be replaceable: the OS, the cluster, the secrets, the edge. So
far, swapping any one of them hasn't meant touching the rest. Every time I've had
to do it, I've learned more than I did from reading about it.
