#+TITLE: The outage that looked like the internet blocking us
#+DATE: 2026-10-25T04:10:00-04:00
#+FILETAGS: homelab:wireguard:mergerfs:monitoring:ops
#+DESCRIPTION: A dead WireGuard endpoint, an endpoint route pointing into its own tunnel, and an hour spent blaming indexers. What the failure looked like, how it was diagnosed, and the monitoring that now catches it.

I spent an hour convinced that book indexers were blocking this homelab. They
were innocent. Our own uplink was dead, and every application reported it
differently.

This is the honest version of that hour, because the failure mode is common and
the diagnosis is cheap — but only if you look at the right layer first.

* What I saw

The media node had stopped downloading books that clearly existed. Searches
through Prowlarr returned nothing. A newly added indexer answered
"all selected indexers unavailable". Anna's Archive and two library mirrors
returned `000` from `curl`.

So I built a theory: these sites block datacenter IPs and VPN egress, which is
why book acquisition is hard on a homelab.

Every part of that theory was wrong.

* What was actually true

Two things, and neither had anything to do with the sites.

#+begin_src sh
wg show proton0
#   latest handshake: 37 minutes ago
#   transfer: 280 GiB received, 9 GiB sent
#+end_src

The tunnel was up as an interface, the unit was `active`, `Result=success`. But
the endpoint had stopped answering. Packets left, nothing came back.

And the reason nothing came back is the second fault:

#+begin_src sh
ip route get 205.142.240.210
#   205.142.240.210 dev proton0 table 51820 src 10.2.0.2
#+end_src

The route to the VPN *endpoint* pointed into the VPN *tunnel*. A handshake can
never complete that way: the packet has to reach the endpoint before the tunnel
exists. Full bootstrap deadlock — and it looks exactly like an idle tunnel.

Proton had rotated the server, so the old IP was dead anyway. Two faults, one
symptom.

* The check I should have run first

One command would have saved the hour:

#+begin_src sh
for h in example.com registry.npmjs.org api.telegram.org; do
  printf '%-22s ' "$h"
  curl -sS -o /dev/null --connect-timeout 8 -w '%{http_code}\n' "https://$h/"
done
#+end_src

Everything returned `000` with `conn=0.000000s`. When *every* destination fails,
including ones nobody blocks, the problem is your egress. A site-specific block
fails one host. A dead tunnel fails all of them.

That is now the first line of the runbook page: prove egress before blaming a
site.

* The fix that does not take the node down

I made it worse before better. My first move was
`systemctl restart wg-quick-proton0`, and the machine never came back: ARP
answered, nothing above layer 2, and it needed a physical power-cycle. A node
whose only route to the world is the tunnel it just tore down is a node you
cannot reach to fix.

The correct move is to swap the peer in place, with no teardown:

#+begin_src sh
wg set proton0 private-key /tmp/new-key
wg set proton0 peer <server-pubkey> endpoint 176.113.74.82:51820 \
       allowed-ips 0.0.0.0/0,::/0 persistent-keepalive 25
#+end_src

Plus the endpoint pin, so the deadlock cannot return:

#+begin_src sh
ip route replace 176.113.74.82/32 via 192.168.2.1 dev eno1 table main
#+end_src

Handshake inside ten seconds. `registry.npmjs.org` returned 200.

* What the sites actually do

With real egress, retested:

| Target | Result |
|--------|--------|
| `ebookbay.com` | **200** |
| `audiobookbay.lu` | **200** |
| `libgen.li` | 200 |
| `annas-archive.org` | unreachable (fails at DNS from pods) |
| `libgen.is`, `library.lol` | dead mirrors |

So the one site I had declared "blocking our egress" answers fine. EBookBay is
now reachable and still fails *inside* Prowlarr, which makes it a definition
problem, not a network one. AudioBookBay answers but has no Prowlarr definition,
so audiobooks need a definition and a torrent client — configuration work, not a
wall.

The lesson generalises: "the site blocks us" is a claim that needs a control
target before you write it down.

* Monitoring, so the next one is not an hour

Nothing watched the tunnel. Disk alerts watched the pool, `NodeDown` watched the
node, and both were green while no *arr could reach an indexer.

node_exporter has no WireGuard collector, so the host writes the metrics itself: a
30 second systemd timer dumps handshake age and transfer counters into
`/var/lib/node-exporter/textfile/`, which node-exporter now scrapes.

| Alert | Condition |
|-------|-----------|
| `WireGuardNoHandshake` | handshake older than 5 minutes — critical |
| `WireGuardHandshakeStale` | older than 3 minutes for 10 minutes |
| `WireGuardMetricsMissing` | no metrics at all |

`persistentKeepalive` is 25s, so a healthy tunnel re-handshakes well inside the
three minute window. The thresholds come from that number, not from taste.

* What I would change

- Prove egress before writing "the site blocks us" anywhere. One `curl` loop with
  a control target is enough.
- Never restart the tunnel interface on a host you cannot reach out-of-band. Pin
  the endpoint route, swap the peer live, persist afterwards.
- Monitor the thing your application depends on, not the thing that is easy to
  measure. The pool had two alerts and the VPN had none, because disks are
  visible and uplinks are not.
- Keep the honest number. The library is smaller than it looked for an hour, and
  the reason was ours.
