When I started, secrets were the thing I understood the least. They also showed me,
again and again, that I did not understand the rest.

The rule I ended up with is simple: no secret sits in git as readable text. To get
there, I made a couple of wrong turns.

* On the machine: SOPS with age

The secrets for the machines (the tunnel credentials, the cluster token) stay
encrypted in the NixOS repo. They are decrypted when the machine starts. For this, the
machine uses its own SSH host key. There is no service to run, and nothing to redo
when I rebuild a machine. So I have never wanted to change this part.

#+begin_src shell
sops secrets/homelab.yaml    # edit; re-encrypts on save
#+end_src

* In the cluster: I started with Sealed Secrets

My first cluster setup was Sealed Secrets. A controller in the cluster holds a private
key. The matching public key encrypts a secret. The encrypted file is then safe to
commit.

#+begin_src shell
kubectl create secret generic app \
  --from-literal=KEY=value --dry-run=client -o yaml \
  | kubeseal --format yaml > sealed-secret.yaml
#+end_src

It felt self-contained. I did not see the problem until the cluster grew. *Every
cluster has its own sealing key.* So a sealed secret only opens on the one cluster it
was sealed for. If you lose that cluster, you lose its key, and the secret is gone
forever. I picked this tool by copying what other people did. I did not think about
having more than one cluster.

* What I use now: Bitwarden, put in by External Secrets

I moved the cluster part to a managed store: *Bitwarden Secrets Manager*. A tool
called *External Secrets Operator* then puts the values into the cluster. The values
live *outside* the lab. So if I wipe a cluster, I do not lose them. And to change a
password, I edit it in Bitwarden. I do not have to seal a file again. The machine part
stayed on SOPS.

I would like to say that I worked this out by thinking. The truth is simpler. The
sealing-key problem forced me to move. And the managed store is what made the problem
go away. Sealed Secrets is gone now.

* The rule, and the mistake

Plain text never goes into git. If a value has to live in the repo, I encrypt it
first. And back up the keys to whatever store you choose. Without those keys, nothing
opens again. I learned that the slow way. That is the only way I seem to learn.

With secrets sorted, I turned back to the cluster itself. And there I found a mistake I
had been making from the very start.
