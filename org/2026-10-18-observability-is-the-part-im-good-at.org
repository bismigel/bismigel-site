Part 7 made the edge harder to kill. This part makes it visible, which is the real end
of the build: a lab I can leave alone because it tells me when something is wrong.

The lab version is small — one namespace, a couple of small controllers, the same three
nodes as everything else. The shape is the shape I would use anywhere.

* A dashboard you never open is decoration

Most homelabs have a Grafana screenshot and nothing behind it. You look at it for a week
and forget it exists. The next time you open it, something has already broken.

A dashboard should answer a question I actually ask. An alert should be something I would
get out of bed for. If neither is true, it is noise with pretty colours. The monitoring is
also files in git — datasources, dashboards, rules, receivers — because clicking in the UI
leaves nothing to review. I only log in to look.

* The stack, with versions

| Component | Version | What it does |
|-----------+---------+--------------|
| Prometheus | 2.51.0 | Pulls metrics every 15s, evaluates rules, keeps 1GB of history |
| Alertmanager | 0.27.0 | Groups, deduplicates and sends alerts to Telegram |
| Grafana | 10.4.0 | Draws the five dashboards; login through Cloudflare Access |
| node-exporter | 1.7.0 | Host CPU, memory, disk, network and load on all three nodes |
| kube-state-metrics | 2.13.0 | Kubernetes object state: pods, deployments, PVCs, nodes |
| Kepler | 0.6.2 (chart) | Per-node and per-pod energy use |
| etcd-metrics-proxy | socat 1.8.0.0 | Relays k3s's loopback etcd metrics to the node network |
| Cloudflare edge exporter | 1.1.0 (mine) | Tunnel, zone, TLS, DNS, Access and RUM state |
| config-reloader | busybox 1.36 | Reloads Prometheus when config or rules change |

Each piece answers a different kind of question and fails in a different way, which is
why I can debug them separately.

* Prometheus pulls; almost nothing pushes

Prometheus is a pull system. Targets are found through Kubernetes service discovery: a
pod or service with the right =prometheus.io/scrape= annotation is added automatically.
The annotation is the contract.

The exception is anything that happens as an event instead of a value. A failed backup is
an event; there is no useful gauge that says "the backup did not run". Those alerts are
pushed to Alertmanager directly.

** Hosts: node-exporter, with one important flag

node-exporter runs as a DaemonSet on every node with =hostNetwork= and =hostPID=, so it
sees the real machine instead of a container.

The flag that mattered is =--path.rootfs=/rootfs=. Without it node-exporter read the host
mount list but stat'ed the container's own root, so every host filesystem outside the
usual =/proc=, =/sys= and =/dev= was invisible: the media pool at =/mnt/media= did not
exist and the numbers for =/= were the overlay's. One flag turned a blind spot into a
dashboard.

** Kubernetes: kube-state-metrics, after fixing a silent bug

kube-state-metrics reads the API and turns objects into =kube_*= metrics. It ran with the
=default= ServiceAccount and no RBAC, so every reflector failed, the endpoint served zero
samples, and Prometheus still reported =up=1=. A target that answers is not a target with
data.

The fix was a dedicated ServiceAccount and a ClusterRole limited to the object types KSM
watches: pods, deployments, PVCs, nodes. It cannot read Secrets or ConfigMaps.

** etcd: a relay instead of an exposed port

k3s serves etcd metrics on =127.0.0.1:2381=, an address that does not exist in the pod
network. =--etcd-expose-metrics= would bind =0.0.0.0:2381= with no authentication,
reachable from the LAN, so instead a DaemonSet runs =socat= in each node's host network
namespace:

#+begin_example
127.0.0.1:2381  ──socat──▶  <node-ip>:9101
#+end_example

Prometheus scrapes it through the normal annotation-driven pod job. The firewall needed
the pod CIDR *and* the node IPs: the CNI at the time was Flannel, which rewrote the source
address when traffic crossed nodes.

** Power: Kepler, scraped pod by pod

Kepler estimates energy from hardware counters and runs with =hostNetwork=, so each pod's
IP is its node's IP. Scraping its Service load-balanced each scrape across nodes, so each
node's series appeared and disappeared. Scraping the pods directly, keeping Kepler's own
=instance=<node>= label with =honor_labels: true=, gives three steady lines instead of
gaps.

** Edge: a small exporter I had to write

Cloudflare's request and bandwidth analytics are GraphQL-only, and the free plan has no
GraphQL Analytics API. What every plan exposes over plain REST is the health that pages
me: tunnel status, connector count, zone state, TLS certificate state, DNS record count,
Access applications.

The exporter is plain Python. Every 60 seconds it takes a snapshot over REST and caches it
in memory, so a slow Cloudflare API never slows a scrape. It runs as a non-root user with
a read-only root filesystem and no capabilities; the token is read-only and comes from
Bitwarden through External Secrets. Web Analytics (RUM) is free on every plan and already
collecting, so the exporter also queries that one account-scoped GraphQL dataset;
everything else stays on REST. When Cloudflare is slow or the token expires,
=cloudflare_api_up= and =cloudflare_export_timestamp_seconds= show it — the exporter does
not hide its own failure.

** Backups: the one thing that pushes

The systemd backup units have =OnFailure= hooks that post an alert to Alertmanager. I do
not infer a failed backup from a missing metric; the job says it failed. That was the
lesson from the cluster post, where a backup I believed in had been failing for who knows
how long.

* Rules reload themselves

Prometheus runs with =--web.enable-lifecycle=. A busybox sidecar hashes the config and
rule files every 10 seconds and calls =/-/reload= when the hash changes. It is the
difference between editing a rule and waiting for a rollout, and editing a rule and
watching it take effect — and it is why rules can live in a ConfigMap and still behave
like code.

* Five dashboards, five questions

| Dashboard | The question | What is on it |
|-----------+--------------+---------------|
| Homelab Overview | Is the lab healthy right now? | Nodes ready, firing alerts, pods, containers not ready, ArgoCD health, media free; CPU, memory, load, network and filesystem trends; pods by phase; restarts |
| Homelab Storage & Media | Will the media pool fill? | Used, free and total bytes; projected time to full; filesystems on the media box; PVC usage; largest container logs |
| Homelab Control Plane | Is etcd and the API healthy? | Members reporting, leader changes, DB size against quota, WAL fsync and backend commit p99, peer round-trip, proposals, node conditions, API storage, targets down |
| Homelab Power | What is using the watts? | Cluster watts, 24-hour energy, average, nodes reporting, per-node and per-component power, top pods |
| Homelab Edge (Cloudflare) | Is the front door healthy? | Tunnel status, connectors, edge connections by colo, active zones, DNS records, certificates, Access apps, snapshot age, API latency, RUM pageviews |

Overview is the screen I keep open: the numbers I check at a glance, the trends per
machine, and the live table of firing alerts. If the top row is green and the table is
empty, I can walk away.

The other four are for when that screen is not enough. Storage is a mergerfs union of four
branches across two hosts, so it gets its own view and its own alerts. Control Plane is
about quorum and disk latency, not CPU. Power is curiosity that turned out to be useful.
Edge is the one that told me whether the tunnel was doing what Part 7 promised.

** How the separation works

Each dashboard is its own ConfigMap and its own file: =grafana-dashboard-overview=,
=-storage=, =-control-plane=, =-power= and =-edge=. Grafana mounts them through a
projected volume and a file provider that checks for changes every 30 seconds.

Splitting them is not tidiness. A storage change is a storage diff. A broken edge query
cannot blank the overview. And a dashboard file is small enough to review.

Two traps:

1. Grafana only reloads a provisioned dashboard when its =version= number goes up. Edit
   the JSON without bumping =version= and nothing happens.
2. In Grafana 10.4, a panel without an explicit datasource can show "No data" even when a
   default datasource exists. Every panel now names the Prometheus datasource by UID.

* Alerts: short, grouped and routed

The rules are grouped by failure domain, not by dashboard:

| Group | Examples |
|-------+----------|
| infra | Node down, target down, disk over 85%, memory over 90%, media pool over 85% and 92% |
| etcd | No leader, fewer than three members reporting, quorum at risk, WAL fsync p99 over 500ms, DB over 1.5GiB |
| cloudflare | Tunnel down, fewer than two connectors, zone not active, zone paused, certificate inactive, exporter stale |
| argocd | App out of sync, app unhealthy |

There are 19 rules, up from the four I started with. The test has not changed: would I act
on this? A CPU spike is not an alert. A disk that will fill in a day is. One connector is
a warning because the edge still works; zero is critical.

Every rule has a =for= duration, so a single bad scrape does not wake me up. Severity is a
label, not decoration. Alertmanager groups by alert name, sends a resolved message when
the problem clears, and repeats every four hours while it is still broken. Login alerts
take a separate route: immediate, no resolved follow-up. Backups and logins are pushed
rather than evaluated, and they end up in Telegram with everything else.

* What I got wrong

- A target can answer and still be useless: kube-state-metrics served zero samples while
  =up= was 1.
- The exporter I checked first was the one reading the wrong root: node-exporter saw no
  media pool until it got =--path.rootfs=.
- The etcd relay was not blocked by the pod CIDR alone; Flannel's source rewriting meant
  the node IPs had to be allowed too.
- A dashboard without a datasource shows "No data", not an error. I spent that time
  looking for a Prometheus problem that was a panel setting.
- Free-plan Cloudflare has no GraphQL request analytics. RUM is the exception, so the
  exporter is shaped around the limit instead of pretending it is not there.

* What it buys

One screen for "is it healthy", four for "why is it not", and a phone that buzzes when
something crosses a line. The edge is monitored from outside as well as inside. The
backups tell on themselves. The media pool warns before an import fails, not after.

The shape is deliberate: pull, don't push; alert on actions; split the dashboards by
question; keep all of it in git. Not finished, but honest, and now it tells me when
something breaks.
