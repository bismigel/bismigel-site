I only started to worry about the front door after something else broke. Then I saw how
much depended on one machine: everything public — the sites, the dashboards, the agent —
came in through one Cloudflare connector on one box. If that process died, or if I rolled
it out badly, the whole lab went dark from outside.

Two things came out of that. The edge got a second connector, so losing a box costs
throughput instead of access. And I learned, slowly, that the same edge is a terrible way
to move video.

* The shape of the problem

A tunnel is made of *connectors*: small processes that dial *out* to Cloudflare and get
handed the traffic for the tunnel. I had one, running as a service on the hosting box,
and the tunnel's routing pointed at that box's ingress:

#+begin_example
ciceley.cc        -> http://192.168.2.82:32080     # the hosting box's ingress
bismigel.dev      -> http://192.168.2.82:32080
...
#+end_example

One connector, on one machine. If it is down, nothing answers.

* The fix

1. Run a **second connector** on the media box, using the same tunnel credentials (kept
   in SOPS).
2. Point every public hostname at the connector's **local** ingress
   (=http://127.0.0.1:32080=) instead of at the other box's IP.

Part two is the one I did not trust until I watched it work. A tunnel's rules name a
service; with =127.0.0.1=, that service is the connector's *own* machine, so each
connector hands traffic to its own box and Cloudflare picks whichever connector is alive.
One API call changes every hostname:

#+begin_src yaml
ingress:
  - hostname: ciceley.cc
    service: http://127.0.0.1:32080
  - hostname: bismigel.dev
    service: http://127.0.0.1:32080
  ...
  - service: http_status:404
#+end_src

#+begin_src mermaid
flowchart LR
  user([Internet]) --> cf[Cloudflare edge]
  cf --> c82["cloudflared<br/>.82"]
  cf --> c81["cloudflared<br/>.81"]

  c82 --> i82["127.0.0.1:32080<br/>on .82"]
  c81 --> i81["127.0.0.1:32080<br/>on .81"]

  i82 --> ing[ingress-nginx<br/>in the cluster]
  i81 --> ing
  ing --> apps["sites - APIs - agent"]
#+end_src

* Where the ingress really lives

My first version stood up a whole second ingress-nginx on the other box, because I
thought each connector needed its own. It does not. There is one cluster, and
ingress-nginx lives *in* it. The port it listens on (32080) is served by the cluster on
every node, so =127.0.0.1:32080= on either box reaches the same ingress. The second box
only needed the second connector.

While I was in there I locked the ingress down: k3s now binds its ports to the *loopback*
address on every node, so the port is reachable only from the box itself. The tunnel is
the only way in. That matters, because the ingress trusts an identity header that
Cloudflare adds; if the LAN could reach it directly, someone could fake that header.

* What the tunnel is not for

The next evening I did a stupid thing: I tried to stream Jellyfin through the front door I
had just finished building, with Zero Trust and a login check in front of it. It buffered,
and I did not know why for a long time.

I blamed the box first. The server was converting at **280 frames per second**, about ten
times real time and a third of the way ahead of me. The disk read at about 300 MB/s. Then
I suspected a power-saving throttle that pauses converting; turning it off changed
nothing. Finally I blamed my connection and ran a speed test, ready to sigh:

#+begin_src shell
Ping     30.8 ms
Download 218 Mbit/s
Upload   450 Mbit/s
#+end_src

450 Mbit/s up. My connection is a fire hose, and ten megabits of video would not trouble
it. Everything I measured was fine, because I was measuring the wrong things.

The clue was where the player's requests came from: a **pod's address** inside the
cluster, not my laptop on the same network. Because I opened the domain name instead of
the address, a video from the same room was taking this trip:

#+begin_example
laptop -> my ISP -> Cloudflare edge -> back down the tunnel -> ingress -> Jellyfin
#+end_example

And then the funnier problem. Cloudflare's free plan is explicitly not for "serving video
or a disproportionate percentage of ... large files". There is no switch that says
"throttle this" and no number to turn down. The throttle *is* the rule: I went looking
for a setting and found a paragraph. On top of that, every three-second segment of video
passed through Cloudflare **Access**, a full login check per segment. I had built a
bouncer for a cinema.

The fix took one second: open Jellyfin at its local address (=http://192.168.2.81:8096=)
and it is instant. Away from home the right answer is a VPN (I chose Tailscale), so the
video goes straight to the device and Cloudflare never sees a frame. The tunnel is for the
*door*: dashboards, APIs, login pages.

* The honest catch

This makes the *edge* safe, not everything behind it. The tunnel and the connectors now
survive losing one process or one box, and the ingress is managed by the cluster instead
of by one machine. It does **not** make what is behind the door safe; that is the
cluster's job. Some things (the media apps) are pinned to one box on purpose. The edge
being up only means the door stays open.

* What it buys

The failures I actually expect — a connector that crashes, a bad ingress update, a
process that dies — now mean "one box serves instead of two", not "the whole edge is
down". For one extra service and one =curl=, that is a fair trade.

The lesson I keep re-learning is the same shape: the tunnel is a great tool for exactly
what it is for, and I keep asking it to be something else, then carefully measuring every
part of the house except the one that is broken. "Use the right path for the job" is
useless advice on its own — except I had a 450-megabit upload and a bored server, and I
still chose the slow way, because the slow way had a nice lock on it.

With the edge solid I could relax, but a lab you cannot watch is a lab you cannot trust.
So the next part is about the thing I am actually good at.
