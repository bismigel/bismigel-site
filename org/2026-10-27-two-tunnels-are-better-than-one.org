#+TITLE: Two tunnels are better than one: making the edge HA
#+DATE: 2026-10-27
#+FILETAGS: homelab:kubernetes:cloudflare

The single scariest thing about the lab was the front door. One Cloudflare
tunnel connector and one ingress controller, both on the same box. If either
died, *everything* public went dark: the sites, the dashboards, the agent. That
is a lot of eggs in one process.

This is how I made the edge boring — two connectors, two ingresses, and a
one-line routing change that lets either box answer.

* The shape of the problem

The lab is two single-node clusters. The "hosting" box runs ArgoCD, ingress-nginx
and the `cloudflared` connector; the "media" box runs the media stack. Public
hostnames come in through a Cloudflare Tunnel, and the tunnel's routing pointed
at one place:

#+begin_example
ciceley.cc        -> http://192.168.2.82:32080     # the hosting box's ingress
bismigel.dev      -> http://192.168.2.82:32080
...
jellyfin.bismigel.dev -> http://192.168.2.81:30096
#+end_example

So the ingress and the connector were both a single point of failure on `.82`.
A node failure, a crash, or even a bad rollout of either one took the whole edge
with it. Two separate failure domains sharing one blast radius.

* The plan

The fix has three parts, and none of them are exotic:

1. Run a **second `cloudflared` connector** on the media box. Cloudflare
   load-balances a tunnel across all its connectors, so two connectors means the
   tunnel survives one of them dying.
2. Run a **second ingress-nginx** on the media box, on the *same* NodePort
   (`32080`) as the first.
3. Point each public host at the connector's **local** ingress
   (`http://127.0.0.1:32080`) instead of a hard-coded peer IP. Now every
   connector serves from the ingress sitting next to it.

That last point is the one that makes it click. A tunnel's ingress rules name a
service; with `127.0.0.1` that service is *the connector's own neighbourhood*.
So both boxes can serve, and Cloudflare picks whichever connector is alive.

#+begin_src yaml
# tunnel ingress (remote-managed, set via the API)
ingress:
  - hostname: ciceley.cc
    service: http://127.0.0.1:32080
  - hostname: bismigel.dev
    service: http://127.0.0.1:32080
  ...
  - service: http_status:404
#+end_src

* Doing it (the parts that matter)

**The second connector.** Both boxes run cloudflared as a NixOS service off the
same tunnel credentials (kept in SOPS). The media box had none, so it was a
matter of adding the service and the secret:

#+begin_src nix
services.cloudflared = {
  enable = true;
  tunnels."<tunnel-id>" = {
    credentialsFile = "/root/.cloudflared/<tunnel-id>.json";
    default = "http_status:404";
    ingress = { "ciceley.cc" = "http://127.0.0.1:32080"; /* ... */ };
  };
};
sops.secrets."cloudflared_credentials" = {
  path = "/root/.cloudflared/<tunnel-id>.json";
  owner = "root"; mode = "0400";
};
#+end_src

The tunnel is remote-managed, so the `ingress` map above is just a local
fallback; the authoritative routing lives in Cloudflare. But it is worth keeping
roughly in sync so a locally-managed run would still be sane.

**The second ingress.** ingress-nginx is the same Helm chart, so the media
cluster gets its own Application pointing at the same chart and the same
NodePorts:

#+begin_src yaml
source:
  repoURL: https://kubernetes.github.io/ingress-nginx
  chart: ingress-nginx
  helm:
    values: |
      controller:
        service:
          type: NodePort
          nodePorts: { http: 32080, https: 32443 }
destination:
  name: calamansi-intel        # the other cluster
  namespace: ingress-nginx
#+end_src

Because it is ArgoCD, it is the same manifest shape as the first one — just a
different `destination`. Adding the redundant copy was a ten-line file.

**The routing.** Finally, the tunnel config flips every public hostname from
`http://192.168.2.82:32080` to `http://127.0.0.1:32080`. One API call:

#+begin_src shell
curl -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$ACC/cfd_tunnel/$TID/configurations" \
  -H "Authorization: Bearer $CF" --data @tunnel-cfg.json
#+end_src

* The honest caveat

This makes the *edge* highly available — the tunnel and the ingress survive a
failure of either. It does **not** make the *apps* HA. The sites and dashboards
still run on the hosting box; if that whole node dies, the surviving connector
reaches the media box's ingress, which has no matching Ingress resource and
returns 404. Edge HA is necessary for app HA, not sufficient.

To go further you would mirror the (stateless) apps onto both clusters so either
ingress has a backend. That is the next step, and it is a bigger one — it means
the apps have to be cluster-agnostic, which is a real design decision rather than
a config flip.

* What it buys

For a homelab, this is the right stopping point: the most likely failures — a
crash-looping connector, a bad ingress rollout, a process dying — now degrade to
"one box serves instead of two" rather than "the whole edge is down". The tunnel
shows two healthy connections, the sites answer, and the front door stops being
the thing I worry about. That is worth ten lines of YAML and one `curl`.
